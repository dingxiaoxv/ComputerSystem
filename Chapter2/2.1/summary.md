# §2.1 信息存储

这一节的主线是：**信息只是一串字节，类型决定字节如何被解释**。同一段位模式作为 `int`、`float`、指针读出来完全不同；十六进制是位的可读视图，字节序、位运算和移位则是日常与字节打交道的三个核心工具。

---

## 十六进制

**🎯 为什么用十六进制**

每 4 位二进制刚好等于 1 个十六进制位，可读性远高于二进制，又能保留位级语义（不像十进制那样模糊掉位边界）。

| 十六进制 | 十进制 | 二进制 |
|---------|--------|--------|
| A | 10 | 1010 |
| B | 11 | 1011 |
| C | 12 | 1100 |
| D | 13 | 1101 |
| E | 14 | 1110 |
| F | 15 | 1111 |

**🎯 2 的幂转十六进制的窍门**

若 $x = 2^n$，令 $n = i + 4j$（$0 \le i \le 3$），结果就是 $2^i$ 后跟 $j$ 个 0。

```
2^11 = 2^(3 + 4×2)  →  i=3, j=2  →  0x800
2^16 = 2^(0 + 4×4)  →  i=0, j=4  →  0x10000
```

## 数据大小

**🎯 类型宽度依赖平台**

| 类型 | 32 位系统 | 64 位 Linux | 64 位 Windows |
|------|---------|-------------|--------------|
| `char` | 1 | 1 | 1 |
| `int` | 4 | 4 | 4 |
| `long` | 4 | **8** | **4** |
| 指针 | **4** | **8** | **8** |

**⚠️ 不要写死字节数**

可移植代码必须用 `sizeof` 或 `<cstdint>` 的定宽类型（`int32_t`、`int64_t`），不要假设 `long` 是 8 字节。

---

## 字节序

**🎯 小端 vs 大端**

- 小端（Little-Endian）：低有效字节在低地址；`0x12345678` 存为 `78 56 34 12`
- 大端（Big-Endian）：高有效字节在低地址；`0x12345678` 存为 `12 34 56 78`

x86 / x86-64 / ARM 默认 / Apple Silicon / RISC-V 都是小端；网络协议（TCP/IP）强制大端。

**🔧 字节序只在跨边界时暴露**

同一台机器上的纯计算永远感知不到字节序——只有**调试器直接看内存、网络传输、读写二进制文件**这三种场景才需要处理。

```c
uint32_t htonl(uint32_t hostlong);   // 主机 → 网络字节序（大端）
uint32_t ntohl(uint32_t netlong);    // 网络 → 主机字节序
```

## 位运算

**🎯 掩码运算**

用 `&` 把不关心的位清零，只保留目标位。

```c
x & 0xFF             // 提取低 8 位
x & 0x80000000       // 检查 32 位符号位
ip & 0xFFFFFF00      // 提取 IPv4 网络地址前 24 位
```

**🎯 移位运算**

| 类型 | 行为 | 等价 |
|------|------|------|
| 左移 `<<` | 右侧补 0 | 乘以 $2^k$ |
| 逻辑右移 `>>` | 左侧补 0 | 无符号数除以 $2^k$ |
| 算术右移 `>>` | 左侧补符号位 | 有符号数向下取整除以 $2^k$ |

**⚠️ 有符号右移是实现定义的**

C 标准未规定有符号数右移补什么，只是 GCC / Clang 实际都做算术右移。可移植代码不应依赖这一行为，需要明确语义时改用无符号类型再移位。

---

## 易错点

- 有符号数右移补什么是实现定义的，不是 C 标准强制行为，跨编译器移植时要警惕
- 字节序在同一台机器内的纯计算中完全感知不到，只在调试 / 网络 / 文件这三种跨边界场景才暴露
- `long` 在 Linux 64 位是 8 字节、Windows 64 位仍是 4 字节，跨平台代码必须用 `<cstdint>`
- 同一段字节作为 `int` 和 `float` 读出来的数值完全不同，类型决定解释方式，不是数据本身决定
- 用 `0xFF` 这类掩码时要明确它的位宽，`0xFFFFFFFF` 作字面量在 32 位 `int` 下可能是负数

---

## 工程关联

- `htonl` / `ntohl` 在所有网络编程里出现，本质就是按需做字节序翻转；写跨主机协议必须显式调用
- GDB / `xxd` / `hexdump` 直接看内存能立刻暴露字节序问题，是调试 C 程序的常用手段
- ELF 文件、网络抓包（pcap）、磁盘镜像分析都依赖位级阅读能力，十六进制是基础阅读单位
- 浮点 IEEE 754 的"为什么 `0.1` 看起来不是 `0.1`"也要靠 `show_bytes` 这种字节级观察才能直观回答

## 实验题

**🧪 题 1：`show_bytes` 验证字节序与类型解释**

```cpp
void show_bytes(const unsigned char* p, size_t n) {
    for (size_t i = 0; i < n; ++i) printf("%.2x ", p[i]);
    putchar('\n');
}

int main() {
    int   i = 12345;
    float f = 12345.0f;
    int*  p = &i;
    show_bytes((unsigned char*)&i, sizeof i);
    show_bytes((unsigned char*)&f, sizeof f);
    show_bytes((unsigned char*)&p, sizeof p);
}
```

要求：

- 编译运行，确认 `int 12345` 输出 `39 30 00 00`（验证小端 + `0x3039 = 12345`）
- 解释 `float 12345` 输出和 `int` 完全不同的原因
- 观察指针 8 字节中高 2 字节为 0，对应 x86-64 实际只用 48 位有效地址

**🧪 题 2：算术右移 vs 逻辑右移在 C 里的差异**

```cpp
int          a = -1;
unsigned int b = 0xFFFFFFFF;
std::cout << (a >> 1) << "\n";   // -1 还是大正数？
std::cout << (b >> 1) << "\n";   // 一定是 0x7FFFFFFF
```

要求：

- 预测两个输出
- 编译运行，确认有符号 `-1 >> 1` 仍是 `-1`（算术右移）
- `gcc -S` 看汇编里两条移位指令的差异（`sarl` vs `shrl`）

**🧪 题 3：字节序对网络传输的影响**

写一个发送方和接收方（同一进程内模拟即可）：

- 发送方把 `uint32_t = 0x12345678` 直接 memcpy 到 buffer，再 memcpy 出来
- 同样的 32 位值经过 `htonl` → `ntohl` 后 memcpy
- 在 little-endian 机器上对比 buffer 字节内容

要求：

- 解释为什么"不经过 `htonl` 也能在自家机器上正确还原"
- 说明跨机器传输时为什么必须 `htonl`

**🧪 题 4：`sizeof` 跨平台陷阱**

```cpp
std::cout << sizeof(long) << " " << sizeof(void*) << "\n";
```

要求：

- 在 64 位 Linux 编译运行，记录输出
- 解释为什么在 Windows 64 位上 `sizeof(long) == 4`，并指出哪些类型可以替代
- 写出一个仅在 Linux 上正确、移到 Windows 后会出 bug 的代码片段
