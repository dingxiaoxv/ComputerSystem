# §2.3 整数运算

这一节的主线是：**所有整数运算在底层都是模运算**。加减乘都在固定位宽的环上进行，溢出就是把高位截断；有符号 / 无符号的差别不在指令本身，而在结果如何被解释，以及由此带来的 UB 边界。

---

## 无符号加法

**🎯 模运算定义**

无符号加法的结果是 $(u + v) \bmod 2^w$，溢出时相当于多减了 $2^w$。

**🎯 溢出检测**

如果 `x + y < x`（或 `< y`），就发生了进位溢出——结果绕回到了一个更小的值。

```c
bool uadd_ok(unsigned x, unsigned y) {
    return (x + y) >= x;
}
```

**⚠️ 无符号溢出是合法行为**

C/C++ 标准明确规定无符号溢出按模 $2^w$ 处理，不是 UB，编译器不会"假设它不发生"。

---

## 补码加法

**🎯 截断后再解释**

把两个补码加起来当成 $w$ 位无符号数算，截断到 $w$ 位，再按补码解释。

**🎯 两类溢出**

- 正溢出：两个正数相加得到负数（结果减了 $2^w$）
- 负溢出：两个负数相加得到正数（结果加了 $2^w$）

```c
bool add_ok(int x, int y) {
    if (x > 0 && y > 0) return x + y > 0;
    if (x < 0 && y < 0) return x + y <= 0;
    return true;
}
```

**⚠️ 有符号溢出是 UB**

这是 §2.3 最重要的一个差异点：有符号溢出在 C/C++ 里是未定义行为，编译器可以假设它不会发生，并据此优化。

---

## 补码取反

**🎯 不对称的范围**

$-x = -x$ 对绝大多数补码数成立，但 $-\text{TMin}_w = \text{TMin}_w$——因为 $-\text{TMin}_w = 2^{w-1}$ 在 $w$ 位补码里表示不出来。

```c
int x = INT_MIN;
int y = -x;   // y == INT_MIN，仍然是负数
```

**🎯 位运算实现**

`-x == ~x + 1`，这就是补码"取反加一"的硬件实现路径。

---

## 无符号乘法和补码乘法

**🎯 低位结果相同**

无符号乘法 $p = (u \cdot v) \bmod 2^w$ 直接截断高位；补码乘法先截断再重新解释。

**关键结论**：对相同的位模式，两者**低 $w$ 位完全一致**，所以 x86 的 `imul`（双操作数形式）不区分有符号/无符号。

```asm
imulq %rsi, %rdi    # 不管两个操作数是有符号还是无符号，低 64 位结果一样
```

只有需要完整 $2w$ 位结果时（单操作数 `imulq` / `mulq`），才必须区分。

---

## 乘以常数：替换为移位 + 加减

**🎯 编译器的常见变换**

移位比乘法快，编译器会把 `x * C` 拆解为若干 `<<` 和 `+`/`-`：

$$x \times 14 = (x \ll 3) + (x \ll 2) + (x \ll 1)$$

或者：

$$x \times 14 = (x \ll 4) - (x \ll 1)$$

**🔧 编译器选最短的序列**

`-O1` 之后会自动这么做，且常和 §3.5 的 `leaq` 合并使用（`leaq (%rax,%rax,4)` 一步完成 `x * 5`）。

---

## 除以 2 的幂

**🎯 无符号 / 正数：直接右移**

`x >> k` 等价于 $\lfloor x / 2^k \rfloor$，逻辑右移和算术右移在正数下结果相同。

**⚠️ 负数右移方向不对**

算术右移是**向负无穷取整**，而 C 整数除法规定**向零取整**，两个方向相反。负数必须先加偏置：

```c
// 编译器对 (有符号) x / 4 的实现
(x + (x >> 31 & 3)) >> 2   // 等价于 (x < 0 ? x+3 : x) >> 2
```

`-7 / 2 == -3`，但 `-7 >> 1 == -4`——差的就是偏置那一位。

| 类型 | 操作 | 等价表达式 |
|------|------|-----------|
| 无符号 | `x >> k` | $\lfloor x / 2^k \rfloor$ |
| 有符号正数 | `x >> k`（算术）| $\lfloor x / 2^k \rfloor$ |
| 有符号负数 | `(x + (1<<k) - 1) >> k` | 向 0 取整 |

---

## 易错点

- `INT_MIN` 取反结果还是 `INT_MIN`，因为补码正负范围不对称
- 有符号溢出是 UB，编译器会消除 `x + 1 > x` 这类形式的"溢出检查"
- 无符号溢出是合法的模运算，不是 UB，可以放心依赖其行为
- `size_t` / `unsigned` 做循环计数器时 `i >= 0` 恒为真，容易死循环
- 负数右移不等于除法，相差一个偏置；汇编里看到 `sar + and + add` 序列就是在做这个修正
- 内存分配里 `n * sizeof(T)` 的乘法可能溢出，`calloc` 内部会检查而 `malloc` 不会
- 移位位数 `>=` 类型宽度是 UB（如 `int x = 1 << 32`），位标志要用无符号类型

---

## 工程关联

- GCC `-O2` 假设有符号整数不溢出，会把 `if (x + 1 > x)` 直接折叠为 `true`——常见的"调试时正常、release 异常"根源
- `std::vector::size()` 返回 `size_t`，与 `int` 比较会触发 `-Wsign-compare`，本质是 §2.2 学过的有符号→无符号隐式转换
- `calloc(n, size)` 比 `malloc(n * size)` 安全的原因是它内部检查了乘法溢出，glibc 直接返回 NULL
- 看反汇编时碰到 `sar k; and m; add` 组合，几乎总是负数除以 $2^k$ 的偏置修正，不要误读为独立位运算
- GCC/Clang 的 `__builtin_{add,sub,mul}_overflow` 是检测溢出最干净的方法，避免依赖 UB；`-fsanitize=signed-integer-overflow` 是开发期对应的动态检查

## 实验题

**🧪 题 1：有符号溢出 UB 在 `-O2` 下消失**

```cpp
bool is_overflow_wrong(int x) { return x + 1 > x; }   // UB
bool is_overflow_right(int x) { return x == INT_MAX; }
```

要求：

- 分别用 `-O0 -S` 和 `-O2 -S` 编译，对比 `is_overflow_wrong` 的汇编
- 在 `-O2` 下应该看到函数体被优化成 `mov eax, 1; ret`
- 解释为什么 `-O0` 没被优化掉

**🧪 题 2：负数右移和除法的方向差**

```cpp
int main() {
    std::cout << (-7 / 2) << " vs " << (-7 >> 1) << "\n";
    std::cout << (-8 / 2) << " vs " << (-8 >> 1) << "\n";
}
```

要求：

- 验证 `-7 / 2 == -3` 而 `-7 >> 1 == -4`
- 解释为什么 `-8` 的两种结果相等（位模式末两位都是 0，无需偏置）
- 从补码位模式角度推导差值

**🧪 题 3：编译器实现 `x / 4` 的偏置修正**

```cpp
int div4(int x) { return x / 4; }
```

要求：

- `-O2 -S` 看汇编，找出 `sar`、`and`、`add` / `lea` 偏置组合
- 手算 `x = -7` 经过这套指令后的中间值，确认最终结果是 `-1`
- 对照 §2.3.7 公式 `(x + (1<<k) - 1) >> k`

**🧪 题 4：`size_t` 循环计数器死循环**

```cpp
std::vector<int> v = {1, 2, 3};
for (size_t i = v.size() - 1; i >= 0; i--) {
    std::cout << v[i] << "\n";
}
```

要求：

- 不修改循环结构，先预测会发生什么
- 编译运行确认是死循环（或在第 0 次后下溢访问越界）
- 改用 `int` 或者 `for (size_t i = v.size(); i-- > 0;)` 写出正确版本

**🧪 题 5：`__builtin_mul_overflow` vs 朴素检查**

```cpp
size_t n;
std::cin >> n;
int* p = new int[n * n];   // 朴素：n*n 可能溢出
```

要求：

- 改写为 `__builtin_mul_overflow` 检查版本，溢出时报错
- 输入 `n = 1 << 33`（64 位机器上），观察两个版本的差异
- 解释为什么 `calloc(n, n*sizeof(int))` 更安全
