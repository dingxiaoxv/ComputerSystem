# §2.4 浮点数

这一节的主线是：**浮点数是实数的近似，不是精确表示**。IEEE 754 用"符号 + 阶码 + 尾数"统一了浮点格式；正因为有限位数的舍入，浮点运算不满足结合律和分配律，`==` 比较几乎总是错的，从整数转 float 在 $2^{24}$ 之后就开始丢精度。

---

## IEEE 754 格式

**🎯 三段式编码**

| 类型 | 符号位 | 阶码 | 尾数 | 有效十进制位 |
|------|--------|------|------|-------------|
| `float`（32 位）| 1 | 8 | 23 | ~7 |
| `double`（64 位）| 1 | 11 | 52 | ~15 |

实际值为 $(-1)^s \cdot M \cdot 2^E$。

**🎯 阶码三种状态**

| 阶码值 | 含义 |
|--------|------|
| 全 0 | 非规格化数（含 ±0） |
| 全 1 | 特殊值（±∞、NaN） |
| 其他 | 规格化数，$E$ = 阶码 - 偏置（float 是 127，double 是 1023） |

**🎯 规格化数隐含前导 1**

规格化数的尾数实际是 $1.xxx\ldots$，最高位的 1 不存进位模式里，免费多得一位精度。所以 float 实际有 24 位尾数精度（23 显式 + 1 隐含）。

---

## 舍入规则

**🎯 默认向偶数舍入**

IEEE 754 默认是 "round half to even"，不是日常理解的"四舍五入"：

| 值 | 向偶数舍入结果 |
|----|----------------|
| 0.5 | 0 |
| 1.5 | 2 |
| 2.5 | 2 |
| 3.5 | 4 |

**🔧 为什么不用四舍五入**

大量数据累积时，"四舍五入"会**系统性偏高**（0.5 总向上）；向偶数舍入让一半向上、一半向下，长期统计无偏。金融、科学计算依赖这种无偏性。

---

## 浮点不满足代数定律

**⚠️ 结合律失败**

```c
(1e20 + (-1e20)) + 3.14   // = 3.14
1e20 + (-1e20 + 3.14)     // ≈ 0.0   ← 3.14 被 1e20 吞掉
```

**⚠️ 分配律失败**

```c
1e20 * (1e20 - 1e20)         // = 0.0
1e20 * 1e20 - 1e20 * 1e20    // = NaN（∞ - ∞）
```

**🔧 编译器不能随意重排浮点运算**

默认情况下编译器禁止改变浮点运算顺序——一改就可能改变结果。只有加 `-ffast-math` 才允许重排，代价是数值精度无法保证。

---

## 浮点陷阱

**⚠️ 大数吃小数**

```c
float x = 1e8f;
x = x + 1.0f;
printf("%f\n", x);   // 仍然是 100000000.000000
```

float 大约只有 7 位有效数字，`1e8` 和 `1e8 + 1` 在 float 里是同一个数。

**⚠️ `==` 比较几乎永远错**

```c
double a = 0.1 + 0.2;
if (a == 0.3) { ... }   // 几乎永远 false
```

`0.1`、`0.2`、`0.3` 在二进制下都无法精确表示，两条路径累积的舍入方向不同，差 1 ULP。正确写法是 `fabs(a - 0.3) < eps`。

**⚠️ 整数转 float 在 $2^{24}$ 后丢精度**

```c
int x = 16777217;          // 2^24 + 1
float f = (float)x;
printf("%d\n", (int)f);    // 16777216，丢了 1
```

float 尾数 24 位，能精确表示的整数范围是 $[-2^{24}, 2^{24}]$。`int → float` **不是无损转换**。

**⚠️ NaN 不等于自身**

```c
double n = 0.0 / 0.0;
n == n   // false
n != n   // true
n < 1.0  // false
n > 1.0  // false
```

检测 NaN 必须用 `isnan(x)`，不能用 `==`。

**⚠️ 浮点转 int 溢出是 UB**

| 转换 | 行为 |
|------|------|
| `int → float` | 可能舍入（>= $2^{24}$） |
| `int / float → double` | 精确 |
| `double → float` | 可能舍入 / 溢出为 ±∞ |
| `float / double → int` | 向零截断；**溢出是 UB** |

```c
int x = (int)1e18;     // UB
int y = (int)NAN;      // UB
```

---

## 易错点

- `0.1 + 0.2 != 0.3`，三者在二进制下都无法精确表示，是常态不是 bug
- `float` 能精确表示的最大整数是 $2^{24}$，超过就开始丢精度，`int → float` 不是无损转换
- `NaN` 不等于任何值（包括自己），用 `==` 检测一定失败，必须用 `isnan()`
- 浮点转 int 溢出是 UB，编译器可任意处理，不会自动截到 `INT_MAX`
- 浮点加法不满足结合律，多线程并行求和结果不确定是正常现象，不是数据竞争
- `-ffast-math` 允许重排浮点运算并打破 IEEE 754 严格语义，对精度敏感的代码不能开

---

## 工程关联

- 金融计算从不直接用 `float` / `double`，要用整数分（cents）或定点数表示金额，避免累积误差
- 多线程或 SIMD 并行求和因为结合律不成立，结果可能因调度顺序变化而轻微不同，是设计预期而不是 bug
- 比较浮点必须用 `fabs(a - b) < eps`，`eps` 的选择依赖数量级（绝对 vs 相对误差）
- 处理传感器数据、JSON 解析、机器学习权重时要警惕 `NaN`，常用 `std::isfinite` 一次性挡掉 NaN 和 ±∞
- 高性能数值库（BLAS、Eigen）默认不开 `-ffast-math`，但允许通过 pragma 局部启用，是性能 vs 精度的工程权衡

## 实验题

**🧪 题 1：`0.1 + 0.2 != 0.3` 的位级证据**

```cpp
double a = 0.1 + 0.2;
double b = 0.3;
uint64_t ua, ub;
std::memcpy(&ua, &a, 8);
std::memcpy(&ub, &b, 8);
std::cout << std::hex << ua << "\n" << ub << "\n";
std::cout << std::dec << (long long)(ua - ub) << "\n";   // 差 1 ULP
```

要求：

- 输出两者位模式，确认仅尾数最低位差 1
- 解释这就是 "差 1 ULP" 的含义
- 改用 `fabs(a - b) < 1e-9` 比较，应该返回 true

**🧪 题 2：大数吃小数**

```cpp
float x = 1e8f;
for (int i = 0; i < 100; ++i) x += 1.0f;
std::cout << x << "\n";   // 仍是 1e8 吗？
```

要求：

- 预测：100 次加 1 后 `x` 是 `1e8 + 100` 还是仍为 `1e8`？
- 运行确认
- 改用 `double` 重做，观察差异
- 解释为什么"先把所有 1 加起来再加到 `x`"能改善精度（Kahan 求和的雏形）

**🧪 题 3：`int → float` 在 $2^{24}$ 后的精度损失**

```cpp
for (int x = 16777215; x <= 16777220; ++x) {
    float f = (float)x;
    std::cout << x << " → " << (int)f << "\n";
}
```

要求：

- 找出第一个 `(int)f != x` 的输入
- 解释为什么 `16777217` 被舍入到 `16777216`
- 用 `double` 重做，确认 `2^53` 以前都精确

**🧪 题 4：NaN 的诡异比较行为**

```cpp
double n = 0.0 / 0.0;
std::cout << (n == n)  << "\n";
std::cout << (n != n)  << "\n";
std::cout << (n < 1.0) << "\n";
std::cout << std::isnan(n) << "\n";
```

要求：

- 预测每一行输出
- 解释为什么用 `x != x` 能检测 NaN
- 写一个函数 `bool is_valid(double x)` 同时挡掉 NaN 和 ±∞

**🧪 题 5：结合律失败的实测**

```cpp
double a =  1e20;
double b = -1e20;
double c =  3.14;
std::cout << (a + b) + c << "\n";
std::cout << a + (b + c) << "\n";
```

要求：

- 预测两个输出
- 解释 `3.14` 为什么被 `1e20` 吞掉
- 加 `-ffast-math` 编译再跑一次，对比 `-O2` 默认行为
