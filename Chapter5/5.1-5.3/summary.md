# §5.1-5.3 优化的边界、CPE 度量与基线程序

这三节是整章的方法论铺垫，回答两个问题：**编译器能替我们优化到什么程度（边界在哪）**，以及**怎么用一个可比的数字（CPE）衡量优化效果**。最后用一个贯穿全章的 `combine` 程序作为后续所有优化的基线。

---

## 编译器优化的硬约束：safe optimization

**🎯 核心原则**

编译器只做**安全优化**：优化后的程序必须在**所有可能输入下**与原程序行为完全一致。哪怕某个变换在 99.9% 的情况下都更快且等价，只要存在一个反例输入会让行为改变，编译器就**必须放弃**。这就是编译器普遍保守的根源。

**🎯 优化级别**

| 选项 | 含义 |
|------|------|
| `-O0` | 不优化（默认），逐句翻译，便于调试 |
| `-O1` | 基本优化，本章 CPE 基线大多基于它 |
| `-O2` | 更激进，工业界默认发布级别 |
| `-O3` | 含向量化等更激进变换 |
| `-Og` | 优化但保留可调试性 |

**⚠️** 高优化级别可能让 GDB 单步、变量查看变得困难（变量被优化进寄存器、代码被重排），调试与优化天然冲突。

## 优化障碍一：内存别名（memory aliasing）

**🎯 什么是别名**

两个指针**可能**指向同一内存位置。编译器无法证明它们不重叠时，就必须假设最坏情况。

**🔧 经典反例**

```c
void twiddle1(long *xp, long *yp) {
    *xp += *yp;
    *xp += *yp;          // 两次读 *yp、两次读写 *xp
}
void twiddle2(long *xp, long *yp) {
    *xp += 2 * (*yp);    // 只读一次 *yp、只写一次 *xp，看起来更快且等价
}
```

看似 `twiddle2` 是 `twiddle1` 的等价优化，但当 `xp == yp`（别名）时：

- `twiddle1`：`*xp` 变成 `4 * 原值`（每次都把自己加给自己）
- `twiddle2`：`*xp` 变成 `3 * 原值`

行为不同，所以**编译器绝不会把 twiddle1 优化成 twiddle2**。

**⚠️ 工程含义**

只要函数里有两个同类型指针参数，编译器就被迫保留冗余的内存读写。`restrict` 关键字正是程序员向编译器承诺"这些指针不别名"的手段。

## 优化障碍二：函数调用的副作用

**🎯 编译器一般不跨函数边界优化**

函数可能修改全局状态，编译器默认无法假设调用它"没有副作用"。

**🔧 反例**

```c
long counter = 0;
long f() { return counter++; }      // 有副作用：每次调用改全局状态

long func1() { return f() + f() + f() + f(); }
long func2() { return 4 * f(); }     // 看似等价
```

若 `f` 像上面这样带副作用，`func1`（counter 从 0 加到 3，返回 0+1+2+3=6）与 `func2`（返回 4*0=0）结果完全不同。因此编译器**不会**把四次调用折叠成一次。

**🎯 内联是解药但有限**

`-O1` 以上 gcc 会尝试**内联（inlining）**：把函数体直接展开到调用点，从而打开跨函数优化的大门。但内联只对**当前编译单元内可见**的函数有效，跨文件、递归、函数指针等场景仍然挡在外面。

## CPE：衡量优化的统一标尺

**🎯 定义**

CPE = **Cycles Per Element**，每处理一个元素消耗的时钟周期数。对处理 n 个元素的程序，总周期数近似线性：

```
T(n) ≈ CPE × n + 开销
```

CPE 就是这条直线的**斜率**，常数开销是截距。元素越多，CPE 的主导作用越明显。

**🎯 为什么用 CPE 而不是绝对时间**

- **归一化规模**：直接比 CPE 不受 n 大小干扰，不同问题规模可横向比较
- **用周期而非秒**：时钟周期数不依赖 CPU 主频，跨机器、跨频率更稳定（程序员无法控制实际运行频率，比如 Turbo Boost）

**🔧 怎么测**

用 CPU 周期计数器（如 `rdtsc` 指令、或 `perf stat` 的 `cycles`）测不同 n 下的总周期，做线性拟合，斜率即 CPE。

## 基线程序：combine 与向量抽象

**🎯 向量 ADT**

书中用一个简单的向量数据类型贯穿全章：

```c
typedef struct {
    long len;
    data_t *data;       // data_t 可切换为 int / long / float / double
} vec_rec, *vec_ptr;

long vec_length(vec_ptr v);                       // 返回长度
int  get_vec_element(vec_ptr v, long i, data_t *dest); // 带边界检查的取元素
data_t *get_vec_start(vec_ptr v);                 // 直接拿到 data 数组首地址
```

**🎯 用宏切换运算与类型**

```c
#define IDENT 0
#define OP +          // 改成 1 和 * 就变成求积
```

这样同一份 `combine` 代码，通过宏可生成"整数求和 / 整数求积 / 浮点求和 / 浮点求积"四种组合，方便对比不同运算的 CPE。

**🎯 基线实现 combine1**

```c
void combine1(vec_ptr v, data_t *dest) {
    long i;
    *dest = IDENT;
    for (i = 0; i < vec_length(v); i++) {   // 注意：每次循环都调 vec_length
        data_t val;
        get_vec_element(v, i, &val);        // 每次循环函数调用 + 边界检查
        *dest = *dest OP val;               // 每次循环读写 *dest（内存）
    }
}
```

**🎯 基线 CPE（趋势）**

- `-O0`：约 22~29，逐句翻译，开销巨大
- `-O1`：约 10~12，编译器做了基本优化

后续 5.4~5.6 三节就是逐个干掉这段代码里的三个低效点（循环不变调用、过程调用、内存引用），把 CPE 从 ~10 压到接近 1。

## 易错点

- "编译器足够聪明，会自动优化一切"是错的——编译器受 safe optimization 约束，只要存在一个让行为改变的输入就放弃优化
- 把 `twiddle1` 手写成 `twiddle2` 不是无脑等价变换：当两个指针别名时结果不同，这正是编译器不敢做的原因
- 别名障碍不是"编译器笨"，而是 C 语言语义允许任意指针重叠，编译器没有信息证明它们不重叠
- 函数调用挡住优化的根因是"可能有副作用"，不是调用本身慢；内联能解开这个结，但跨编译单元时通常无效
- CPE 是斜率不是总时间——比较两个版本要看 CPE，别被固定开销（截距）干扰
- 用时钟周期而非纳秒衡量，是因为主频会动态变化，周期数才是稳定可比的量

---

## 工程关联

- `restrict` 关键字（C99）是程序员手动消除别名障碍的工具，告诉编译器指针不重叠，常见于数值计算库、`memcpy` 类实现
- `-O2` 是绝大多数生产构建的默认级别；`-Og` 是"想优化又想调试"时的折中
- `__attribute__((pure))` / `__attribute__((const))` 可向 GCC 声明函数无副作用，解开函数调用障碍，让 `func1` 那样的折叠成为可能
- `perf stat` 输出的 `cycles` 和 `instructions` 是计算 CPE、IPC 的原始数据；CPE 思想本质上是把 cycles 归一化到"每元素"
- 调试 release 版（`-O2`）时变量"optimized out"、断点跳跃，正是优化与可调试性冲突的直接体现

## 实验题

**🧪 题 1：验证别名障碍**

```c
void twiddle1(long *xp, long *yp) { *xp += *yp; *xp += *yp; }
void twiddle2(long *xp, long *yp) { *xp += 2 * (*yp); }
```

要求：

- `gcc -O2 -S` 分别生成两者汇编，确认 `twiddle1` 有两次对 `*yp` 的读和两次对 `*xp` 的写（编译器没敢合并）
- 写主程序：定义 `long a = 1;`，分别用不同指针 `twiddle1(&a,&b)` 和别名 `twiddle1(&a,&a)`，打印结果验证别名下是 4 倍
- 给 `twiddle1` 的参数加 `restrict`，重新 `-O2 -S`，观察汇编是否被优化成只读一次 `*yp`

**🧪 题 2：函数调用阻止优化**

```c
long counter = 0;
long f() { return counter++; }
long func1() { return f() + f() + f() + f(); }
```

要求：

- `gcc -O2 -S` 查看 `func1`，确认确实生成了四次 `call f`，没有折叠成 `4*f()`
- 把 `f` 改成 `static long f() { return 0; }`（无副作用且本编译单元可见），重新编译，观察是否被内联甚至常量折叠
- 解释为什么带副作用版本编译器不敢动

**🧪 题 3：手测 CPE**

```c
data_t combine_sum(data_t *a, long n) {   // 自己写个简化版求和
    data_t s = 0;
    for (long i = 0; i < n; i++) s += a[i];
    return s;
}
```

要求：

- 用 `__rdtsc()`（`#include <x86intrin.h>`）测量 n = 1000、2000、…、10000 时的周期数
- 对 (n, cycles) 做线性拟合，求斜率得到 CPE
- 分别用 `-O0` 和 `-O1` 编译，对比两个 CPE，量化优化级别的影响
