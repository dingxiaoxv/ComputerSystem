# §5.11 一些限制因素

这一节的主线是：**前面的优化（多累加器、重新结合）不是越激进越好——两个硬件限制会反咬一口**

- **寄存器溢出**：并行度一旦超过寄存器数量，临时值被迫"溢出"到栈，load/store 抵消并行收益
- **分支预测失败**：深流水线靠投机执行，预测错了要清空流水线、罚 ~15-20 周期；难预测的数据相关分支才是杀手
- 应对分支失败的手段是"写成适合 cmov 的功能式风格"，把控制相关变成数据相关——这是 §3.6.6 cmov 的正面用法

---

## 寄存器溢出（Register Spilling）

**🎯 并行度的上限是寄存器数量**

§5.9 用多累加器提升并行度时，每个累加器都要常驻一个寄存器。x86-64 只有 **16 个整数寄存器**和 **16 个 YMM 向量寄存器**，扣掉栈指针、循环变量、指针等固定占用，真正能拿来做累加器的也就十来个。

当展开度 `k` 超过可用寄存器数，编译器没法把所有累加器都放进寄存器，只能把一部分"溢出"（spill）到栈上的内存里。

**🎯 溢出的代价：每次迭代多一对 load/store**

寄存器累加器：一条 `imul` 直接读改写寄存器，0 次访存。
溢出到栈的累加器：每次迭代要 `从栈 load → 运算 → store 回栈`，凭空多出两条访存指令。

```asm
# 没溢出：累加器在寄存器里，干净利落
imulq (%rdx,%rax,8), %r8        # acc0 *= data[i]，纯寄存器运算

# 溢出后：累加器被放到栈，每次迭代来回搬
movq   16(%rsp), %rcx           # 从栈把累加器读出来
imulq  (%rdx,%rax,8), %rcx      # 运算
movq   %rcx, 16(%rsp)           # 再写回栈
```

**🔧 书中实测：10×10 反而比 6×6 慢**

CSAPP 给出的整数乘法 `combine`：
- 展开/累加器从 1 路加到 6 路，CPE 持续下降，逼近吞吐量界限（乘法吞吐界限 ~1.00）
- 继续加到 10×10、20×20，CPE **不降反升**——因为累加器装不进 16 个寄存器，开始溢出

汇编里的判别特征：循环体内出现对 `(%rsp)`、`8(%rsp)`、`16(%rsp)` 等栈地址的**反复 mov 读写**，就是溢出的铁证。

**⚠️ 结论**：累加器数量不是越多越好，要卡在"刚好填满可用寄存器"。整数约 10-12 路、向量约能开到向量寄存器数量，再多就溢出倒亏。

## 分支预测与预测失败处罚

**🎯 为什么会有这个开销：深流水线 + 投机执行**

现代处理器流水线很深（Haswell ~15 级）。取指阶段必须**提前**知道下一条指令的地址，但遇到条件分支时，要等分支条件算出来才知道走哪条路——这中间隔了十几级流水线。

处理器不愿空等，于是用**分支预测器**猜一个方向，沿着猜的路径**投机执行**（speculative execution）后续指令。

- 猜对了：流水线满负荷，分支几乎零开销
- 猜错了：已经投机执行的指令全部作废，要把流水线清空、从正确地址重新取指——罚 **~15-20 周期**（书中 Intel Core i7 实测约 19 周期，对应一个 `mispredict penalty`）

**🎯 不是所有分支都要担心**

绝大多数分支是**高度可预测**的，预测器准确率常 >95%，根本不用管：
- 循环回边（`i < n` 几乎每次都成立，只有最后一次不成立）
- 错误检查分支（几乎从不触发）

真正的性能杀手是**数据相关、模式随机、无法预测**的分支——典型是"对随机数据做比较再分支"。

**🔧 写成适合条件传送的功能式风格**

应对手段不是手动消分支，而是**改写代码风格让编译器生成 cmov**（条件数据传送，回顾 [[../../Chapter3/3.6|§3.6.6]]）。cmov 把"控制相关"变成"数据相关"：两条路径的值都算出来，按条件选一个，**不存在跳转，也就没有预测失败**。

经典例子——数组相邻元素的 min/max 分离（如排序内层）：

```c
/* 分支版：数据随机时预测失败率高 */
void minmax1(long a[], long b[], long n) {
    for (long i = 0; i < n; i++) {
        if (a[i] > b[i]) {          // 难预测的数据相关分支
            long t = a[i];
            a[i] = b[i];
            b[i] = t;
        }
    }
}

/* 功能式版：编译器更可能用 cmov 实现 */
void minmax2(long a[], long b[], long n) {
    for (long i = 0; i < n; i++) {
        long min = a[i] < b[i] ? a[i] : b[i];   // 两个值都算，按条件选
        long max = a[i] < b[i] ? b[i] : a[i];
        a[i] = min;
        b[i] = max;
    }
}
```

书中实测对比（CPE）：
- **可预测数据**：分支版反而略快（cmov 要算两边）
- **不可预测（随机）数据**：分支版 CPE 飙升（如 ~13），cmov 版稳定（如 ~4），后者完胜

**⚠️ cmov 不是银弹**（同 §3.6.6 的限制）

cmov 两条路径都会被求值。如果某条路径有副作用、可能解引用非法指针、或计算代价很高，就**不能**用 cmov，编译器也不会生成——这时只能老实用分支。所以"功能式改写"只适用于两边都是廉价、无副作用的纯计算。

## 易错点

- 多累加器不是越多越好：超过寄存器数量会溢出到栈，每次迭代多一对 load/store，CPE 不降反升
- 寄存器溢出的判别看汇编——循环体里出现对 `(%rsp)` 的反复 mov 读写，就是累加器被挤到栈上了
- 不要无差别地"消除分支"：循环边界、错误检查这类分支预测器几乎不会错，手动优化是白费力
- 真正值钱的优化目标是**数据相关、模式随机**的分支，不是所有 `if`
- cmov 把控制相关变数据相关，但两边都求值——有副作用/可能非法访问/代价高的路径不能用 cmov
- 可预测数据下 cmov 反而可能更慢（白算了一条路径），cmov 的收益只在分支难预测时兑现

## 工程关联

- `perf stat -e branches,branch-misses ./prog`：直接看分支预测失败率，`branch-misses / branches` 是关键比值；同一程序喂排序 vs 未排序数据，这个比值会差一个数量级
- StackOverflow 经典问题"Why is processing a sorted array faster than an unsorted array"就是本节现象：对已排序数组，`if (data[i] >= 128)` 的分支高度可预测；乱序时预测器频频失手，慢数倍
- GCC `-funroll-loops` 或手动过度展开可能踩到寄存器溢出——展开度要配合 `-S` 看汇编里有没有栈溢出，而不是盲目加大
- 编译器优化报告里的 "if-conversion" 就是把分支转成 cmov 的变换；`-O2` 下编译器会自行判断该不该做
- 自动向量化（SIMD）天然没有逐元素分支，对随机数据反而稳定——这也是把分支逻辑改成掩码运算（masking）的动机
- topdown 微架构分析里，寄存器溢出表现为 `Memory Bound`/`Store Bound` 上升，分支失败表现为 `Bad Speculation` 占比上升，可一眼区分两类瓶颈

## 实验题

**🧪 题 1：寻找寄存器溢出的拐点**

写一个可配置展开度的整数乘法累加 `combine`，分别实现 1、2、4、6、8、10、12、20 路累加器版本：

```c
/* 6 路累加器示意，其余照此扩展 */
long combine6(long *data, long n) {
    long acc0=1, acc1=1, acc2=1, acc3=1, acc4=1, acc5=1;
    long i;
    for (i = 0; i + 6 <= n; i += 6) {
        acc0 *= data[i];   acc1 *= data[i+1];
        acc2 *= data[i+2]; acc3 *= data[i+3];
        acc4 *= data[i+4]; acc5 *= data[i+5];
    }
    for (; i < n; i++) acc0 *= data[i];
    return acc0*acc1*acc2*acc3*acc4*acc5;
}
```

要求：
- 用 `__rdtsc()` 或 `clock_gettime` 测各版本 CPE，画出 CPE 随累加器数变化的曲线
- 找到 CPE 最低点（拐点），观察它之后 CPE 是否回升
- 对拐点前后两个版本 `gcc -O1 -S`，确认高展开度版本汇编里出现 `(%rsp)` 的 load/store（溢出证据）

#include <stdlib.h>
long sum_above_threshold(int *data, long n) {
    long sum = 0;
    for (long i = 0; i < n; i++) {
        if (data[i] >= 128)     // 待观察的数据相关分支
            sum += data[i];
    }
    return sum;
}

- 数组填 `rand() % 256` 的随机数，分别对**排序后**和**未排序**两份数据各跑多轮

- 验证：排序后 `branch-misses` 比例极低、墙钟时间明显更短；解释为什么排序让分支变得可预测
