# §5.7 理解现代处理器

这一节是整章的分水岭：§5.4-5.6 那些优化**不需要懂处理器**，CPE 压到接近 1 就到头了。想再往下走，必须理解现代处理器的两大特性——**超标量（superscalar）**和**乱序（out-of-order）**——以及由此产生的两个性能天花板：

- **延迟界限（latency bound）**：一串有数据依赖的操作必须顺序执行，关键路径上的延迟逐个累加，决定了 CPE 的下限
- **吞吐量界限（throughput bound）**：功能单元的数量和发射能力决定了每周期最多能完成几个操作，这是处理器性能的硬上限

理解了这两个界限，才知道 §5.8 的循环展开和多累加器到底在突破什么。

---

## 现代处理器的整体结构（§5.7.1）

**🎯 两大部分：ICU 和 EU**

现代处理器在硬件上把"取指译码"和"真正干活"拆成两个部分，并行重叠运行：

| 部分 | 全称 | 职责 |
|------|------|------|
| ICU | 指令控制单元（Instruction Control Unit） | 从指令 cache 取指、译码、做分支预测，把指令拆成微操作（μop） |
| EU | 执行单元（Execution Unit） | 真正执行微操作，包含多个并行的功能单元 |

**🎯 超标量（superscalar）**

一个周期能**发射多条指令**。例如 Haswell 每周期最多发射约 4 条微操作。这就是为什么 CPE 可以小于 1——一个时钟周期内完成不止一个元素的运算。

**🎯 乱序（out-of-order）**

指令的**实际执行顺序**可以和程序里写的顺序不同，只要不违反数据依赖。处理器会动态地找出"现在就能算"的指令提前执行，把因为等待数据而空转的周期填满。

**🎯 投机执行 + 寄存器重命名**

- **投机执行（speculative execution）**：遇到分支时，处理器靠分支预测器猜一个方向，**不等条件算出来就先往下执行**。猜对了直接赚到，猜错了把投机做的工作丢弃（这就是 §5.11 分支预测失败代价的来源）。
- **寄存器重命名（register renaming）**：处理器内部维护一组比 16 个架构寄存器多得多的物理寄存器。同一个 `%rax` 在不同时刻可以映射到不同物理寄存器，从而消除"假依赖"（WAR/WAW），让乱序执行的空间更大。这是值在功能单元之间直接转发、不必经过寄存器堆的关键机制。

**🔧 retirement unit（退役单元）**

投机执行的结果先存在重排序缓冲区里，**等到确认这条指令该执行（分支猜对、无异常）时才"退役"**，把结果真正写回架构状态。一旦发现预测错误，就把这条之后的投机结果全部作废。这保证了乱序+投机对程序员透明——你看到的永远是顺序执行的正确结果。

## 分支预测器（§5.7 延伸）

正文只在投机执行里一笔带过"靠分支预测器猜方向"，但这是理解 §5.11 分支预测失败代价的前置知识。

**🎯 为什么需要它**

流水线很深（Haswell 前端到执行约 14-19 级）。一条 `jne .L3` 到底跳不跳、跳到哪，要等条件码就绪才知道，而条件码可能很晚才算出来。硬等就会让前面十几级流水线空转。分支预测器是**猜方向的硬件**，让取指单元不等结果先顺着猜的方向继续灌指令，这正是投机执行的前提。

**🎯 它内部猜三件独立的事**

| 结构 | 猜什么 | 典型场景 |
|------|--------|---------|
| 方向预测器 | taken / not taken | `if`、循环回边 |
| BTB（分支目标缓冲） | 跳到哪个地址 | 间接跳转、虚函数表 |
| RAS（返回地址栈） | `ret` 回哪 | 和 `call` 配对 |

方向预测的演进：1-bit → 2-bit 饱和计数器 → 两级自适应（全局历史 GHR + 模式历史表 PHT）→ 现代的 **TAGE**、感知机预测器。规律性强的分支命中率可达 99%+。

**🎯 程序员能控制吗：不能直接控制，只能间接影响**

没有任何 x86 指令能对硬件说"这个分支预测成 taken"（P4 时代的 `2E`/`3E` 分支提示前缀，现代 CPU 直接忽略）。能做的是三类间接手段：

- **`__builtin_expect` / `likely()` / `unlikely()`**：它**不编程硬件预测器**，只影响**编译器代码布局**——把热路径放到 fall-through 位置、冷路径搬到函数尾部，改善 I-cache 局部性、让"历史为空时"的静态默认预测更可能对。
- **让分支可预测，或干脆消除分支**：数据有规律时命中率高（经典反例：对**已排序** vs **未排序**数组做 `if (a[i] > 128) sum += a[i]`，逻辑相同但排序后快好几倍）；或用 `cmov`、查表、位运算把"数据相关的分支"变成"数据相关的数据流"——这正是 §5.11 的主题。
- **PGO（profile-guided optimization）**：`-fprofile-generate` 跑真实负载，`-fprofile-use` 让编译器按真实分支频率布局。工程上最靠谱，本质仍是控制布局而非硬件。

一句话直觉：**程序员能做的是"让分支容易被猜对"或"把分支干掉"，而不是"告诉预测器答案"。**

**🔧 实证：`likely/unlikely` 到底改了哪些字节**

两个函数源码逻辑完全相同，只把提示从 `likely` 翻成 `unlikely`（`block_A`/`block_B` 写成多条内联指令，方便观察整块被搬到哪）：

```c
int expect_true(int v) {   // likely(v>0)：认为 A 是热块
    if (likely(v > 0))   { block_A(v); return 1; }
    else                 { block_B(v); return 0; }
}
int expect_false(int v) {  // unlikely(v>0)：认为 B 是热块
    if (unlikely(v > 0)) { block_A(v); return 1; }
    else                 { block_B(v); return 0; }
}
```

`gcc -O2 -c flip.c && objdump -d flip.o` 后，布局差异一目了然：

```
expect_true（A 热）              expect_false（B 热）
  4: test %edi,%edi               74: test %edi,%edi
  6: jle  0x40   ←条件取反         76: jg   0xb0   ←条件取反(jle→jg)
  8: <block_A>  ←热块fall-through  78: <block_B>  ←换 B fall-through
 3d: ret                          a6: ret
 40: <block_B>  ←冷块踢到尾部      b0: <block_A>  ←冷块踢到尾部
 6e: ret                          ...
```

三个可见变化，正好对应上面那条提示的三层含义：

- **热块永远在 fall-through 位置**：被认为常走的块紧跟判断、地址连续，CPU 顺流取指不跳转
- **冷块被整体搬到函数尾部**（`0x40`/`0xb0` 之后）：正常执行不会取到它所在的 cache line，热路径指令在地址上连成一片 → 改善 I-cache 局部性
- **分支指令本身被取反**：同一个 `v>0`，一版编成 `jle`、另一版编成 `jg`——编译器故意翻转比较方向，让"预期走的路"成为**不跳转**的一侧；这恰好命中"前向跳转默认预测不发生"的静态规则，冷启动/预测器被冲刷后的头几次也能押对

实验文件：`Chapter5/5.7/expirements/flip.c`。

## 功能单元的性能（§5.7.2）

**🎯 描述一个功能单元的三个指标**

| 指标 | 含义 |
|------|------|
| 延迟（latency） | 完成一次运算需要的总周期数 |
| 发射时间（issue time） | 两次连续同类运算之间必须间隔的最小周期数 |
| 容量（capacity） | 该类运算有几个功能单元能并行做 |

**🎯 流水线化 → issue time = 1**

issue time 为 1 表示功能单元**完全流水线化**：虽然一次乘法要 5 个周期才出结果，但只要操作之间没有依赖，可以每个周期都塞一个新乘法进去，像流水线一样。

```
完全流水线化的浮点乘法器（latency=5, issue=1）：
周期:  1   2   3   4   5   6   7
乘法A: ─┬───┬───┬───┬───┤(出结果)
乘法B:     ─┬───┬───┬───┬───┤
乘法C:         ─┬───┬───┬───┬───┤
            ↑ 每周期都能发射一个新乘法，互不等待
```

而**除法不流水线化**：issue time 约等于 latency（3~30），必须上一个除法彻底算完才能开始下一个。

**⚠️ 除法为什么是性能毒药（正文没说，表 5.12 藏着答案）**

毒在两个原因叠加，而第二个才是真凶：

1. **延迟高**（浮点除 3-15、整数除 3-30）。但延迟高本身不致命——只要能流水线化，§5.8 多累加器就能救。
2. **不流水线化，issue ≈ latency**（真凶）。除法算法本质是**迭代**的（SRT、恢复余数、牛顿迭代），每步依赖上一步的部分商/余数，硬件做成一个反复迭代的电路。要流水线化得把每级迭代硬件复制成阵列，但除法器面积大、复制代价太高，所以只放一个迭代单元（capacity=1）反复用。乘法用 Wallace 树是组合逻辑，插流水线寄存器就能完全流水线化。

为什么"不流水线化"比"延迟高"杀伤更大——**它连独立运算都救不了**。5 个互相独立的乘法（latency=5, issue=1）约 9 周期重叠做完；5 个独立除法（latency=10, issue=10）要 50 周期，一个算完才发下一个。即 CPE = issue/capacity = latency，**延迟界限和吞吐量界限被焊死在一起**，多累加器对它几乎无效。

规避（呼应 §3.5.7）：除以常数 → 乘魔数+移位；除以 2 的幂 → 移位；除数是变量时编译器无能为力，热路径里要把除法提到循环外（先求倒数再循环内乘），取模用 `& (n-1)` 代替 `% n`。

**🎯 Haswell 参考数据（书中表 5.12）**

| 运算 | 整数 latency / issue / capacity | 浮点 latency / issue / capacity |
|------|--------------------------------|--------------------------------|
| 加法 | 1 / 1 / 4 | 3 / 1 / 1 |
| 乘法 | 3 / 1 / 1 | 5 / 1 / 2 |
| 除法 | 3–30 / 3–30 / 1 | 3–15 / 3–15 / 1 |

读这张表的要点：加法、乘法都是完全流水线化（issue=1）；除法是个"独苗"，又慢又不流水线，是性能毒药。

**🎯 由容量和发射时间推出吞吐量界限**

某类运算每周期最多完成的次数 = `capacity / issue_time`，换算成 CPE 就是 `issue_time / capacity`。整数加有 4 个单元，理论上每周期能做 4 个，CPE 下限 0.25；但 combine 每次迭代还要一次 load，load 单元只有 2 个，所以整数加实际吞吐量界限被卡在 0.50。

## 抽象的处理器操作模型（§5.7.3）

**🎯 把循环画成数据流图**

把 `combine4` 内层循环里的寄存器按角色分四类：

- **只读（read-only）**：循环中只读不改，如向量数据指针、长度
- **只写（write-only）**：只作为目的，如条件码
- **局部（local）**：在一次迭代内产生又用掉，不跨迭代
- **循环（loop）**：既是上一次迭代的输出，又是下一次迭代的输入——**这类寄存器构成了跨迭代的依赖链，是性能分析的核心**

`combine4` 里只有累加变量 `acc` 和循环索引 `i` 是循环寄存器。

**🎯 关键路径（critical path）**

把每次迭代的操作连成图，跨迭代的循环寄存器把一个个操作串成一条长链。对 `acc = acc OP data[i]`，每次迭代的 `OP` 都依赖上一次的 `acc`：

```
acc₀ ──OP── acc₁ ──OP── acc₂ ──OP── acc₃ ── ... ── accₙ
        ↑ 每个 OP 必须等前一个 OP 的结果，无法并行
```

这条由 n 个 `OP` 串起来的链就是**关键路径**。它的总长度 = n × (OP 的延迟)，于是 CPE ≈ OP 的延迟。

**🎯 两个界限的具体数值**

| 运算 | combine4 实测 CPE | 延迟界限 | 吞吐量界限 |
|------|------------------|---------|-----------|
| 整数 + | 1.27 | 1.00 | 0.50 |
| 整数 * | 3.01 | 3.00 | 1.00 |
| 浮点 + | 3.01 | 3.00 | 1.00 |
| 浮点 * | 5.01 | 5.00 | 0.50 |

关键观察：**除了整数加，其余三种运算的实测 CPE 都精确地等于对应运算的延迟**——因为关键路径上的串行依赖链把吞吐能力完全浪费了，处理器有多个乘法器也用不上，只能干等前一个结果。整数加的 1.27 没有贴着延迟界限 1.00，是因为延迟太短（1 周期），瓶颈转移到了循环开销和 load 上，已经接近吞吐量界限。

**🎯 这一节留下的悬念**

延迟界限是 `combine4` 这种"单累加器"写法的死穴：依赖链强制串行。但功能单元明明是流水线化、多份的，吞吐量界限远低于延迟界限。**§5.8 的循环展开 + 多累加器，就是要打断这条单一依赖链，把多条独立的链喂给并行的功能单元，让 CPE 从延迟界限逼近吞吐量界限。**

## 易错点

- 超标量指"每周期发射多条指令"，乱序指"执行顺序可与程序顺序不同"，两者是独立的两个特性，不要混为一谈
- issue time = 1 不代表运算 1 周期完成，而是"每周期能发射一个新运算"，延迟仍可能是 5 周期（完全流水线化）
- 吞吐量界限 CPE = issue_time / capacity，不是 capacity 直接当 CPE；而且实际还会被 load/store 单元数这类别的瓶颈进一步限制
- 关键路径长度由**循环寄存器形成的跨迭代依赖链**决定，只读/局部寄存器不影响它
- 延迟界限是单累加器写法的下限，不是处理器的极限；处理器极限是吞吐量界限，靠打断依赖链才能逼近
- 投机执行做错了不会污染结果——retirement unit 保证只有"确认该执行"的指令才退役写回，对程序员透明
- 分支预测器不可被程序员直接编程，`__builtin_expect`/`likely` 改的是编译器代码布局而非硬件预测器；真正能"控制"分支的是消除分支（cmov/查表）或 PGO
- 除法慢的真凶不是延迟高，而是**不流水线化**（issue≈latency, capacity=1）——这让它的吞吐量界限恶化到等于延迟，多累加器也救不回来

## 工程关联

- `perf stat` 的 **IPC（instructions per cycle）** 直接对应超标量的发射宽度，IPC 远低于 4 且 CPE 卡在某个整数值附近，往往就是撞上了延迟界限（依赖链太长）
- `perf stat` 的 **stalled-cycles-backend** 高，通常意味着功能单元/依赖链成为瓶颈，正是本节描述的场景
- **`llvm-mca`** 和在线工具 **uiCA / uops.info** 能把一段汇编的微操作调度、端口占用、关键路径可视化出来，是把本节"数据流图"落地的实战工具
- 寄存器重命名解释了为什么手写汇编时复用同一个寄存器名不一定造成串行——处理器会重命名消除假依赖，真正的瓶颈是**真数据依赖**
- 除法/取模在热路径里要警惕：它不流水线化、延迟极高，编译器才会想方设法用移位、乘法逆元（§3.5.7）替代它
- 分支预测失败会清空投机执行的流水线，这是 §5.11 要量化的代价，根子就在本节的投机执行机制

## 实验题

**🧪 题 1：验证四种运算贴着延迟界限**

写出 §5.3 的 `combine4`（用宏切换 `data_t` 和 `OP`）：

```c
typedef long data_t;        // 改成 double 测浮点
#define OP *                // 改成 + 测加法
#define IDENT 1

void combine4(vec_ptr v, data_t *dest) {
    long i;
    long length = vec_length(v);
    data_t *d = get_vec_start(v);
    data_t acc = IDENT;
    for (i = 0; i < length; i++)
        acc = acc OP d[i];
    *dest = acc;
}
```

要求：

- 用足够大的向量（如 10⁸ 元素）测每种组合的 CPE（`(end_cycles - start_cycles) / length`，用 `rdtsc` 或 `clock_gettime` 估算）
- 填出整数+/整数*/浮点+/浮点* 四个 CPE，和书中 1.27 / 3.01 / 3.01 / 5.01 对照
- 确认除整数加外，三个 CPE 都≈对应运算的延迟（3/3/5），解释为什么不是吞吐量界限

**🧪 题 2：用 `llvm-mca` 看关键路径**

把 `combine4` 内层循环用 `-O2 -S` 编出汇编，截取循环体喂给 `llvm-mca`：

```bash
gcc -O2 -S combine4.c
# 把内层循环汇编片段存成 loop.s，加上 # LLVM-MCA-BEGIN / # LLVM-MCA-END 标记
llvm-mca -mcpu=native -timeline loop.s
```

要求：

- 在 timeline 视图里找出哪条指令构成跨迭代的依赖链
- 看 `llvm-mca` 报告的 "Block RThroughput" 和实测 CPE 对比
- 解释为什么有多个乘法端口，但浮点乘的 CPE 还是被卡在 5

**🧪 题 3：除法为什么是性能毒药**

写两个函数，一个累加、一个累除：

```c
double sum_loop(double *d, long n) {
    double acc = 0;
    for (long i = 0; i < n; i++) acc += d[i];
    return acc;
}
double div_loop(double *d, long n) {
    double acc = 1e30;
    for (long i = 0; i < n; i++) acc /= d[i];   // 保证 d[i] 不为 0
    return acc;
}
```

要求：

- 测两者 CPE，对照浮点加 latency=3、浮点除 latency=3~15 且不流水线
- 用 `perf stat` 看 IPC，解释为什么除法循环的 IPC 极低
- 总结：为什么"不流水线化（issue≈latency）"比"延迟高"对吞吐量的杀伤更大
