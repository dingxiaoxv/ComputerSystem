# §5.8-5.9 循环展开与提高并行性

这两节连起来回答 §5.7 留下的悬念：`combine4` 被**延迟界限**焊死（CPE = 运算延迟），而功能单元明明是流水线化、多份的，吞吐量界限远低于延迟界限。怎么把 CPE 从延迟界限拉到吞吐量界限？

主线是三步，且**第一步会"失败"**——这正是关键教学点：

1. **§5.8 循环展开（k×1）**：减少循环开销，但**打不断关键路径上的依赖链**，对延迟受限的运算 CPE 纹丝不动
2. **§5.9.1 多累加器（k×k）**：开 k 条独立依赖链并行喂给流水线，CPE 向 `延迟/k` 逼近，直到撞上吞吐量界限
3. **§5.9.2 重新结合**：只用一个累加器，靠加括号把部分运算移出关键路径，同样逼近吞吐量界限

核心一句话：**循环展开省的是"循环开销"，多累加器/重结合破的才是"数据依赖链"——后者才是延迟界限的成因。**

---

## 循环展开（§5.8）

**🎯 什么是 k×1 展开**

一次迭代处理 k 个元素，循环体里重复 k 次 `acc = acc OP d[i+j]`，索引一次跳 k 步。下面是 2×1 的 `combine5`：

```c
for (i = 0; i < limit; i += 2) {       // 主循环，一次走 2 个
    acc = (acc OP d[i]) OP d[i+1];
}
for (; i < length; i++)                // 收尾，处理剩余不足 2 个的
    acc = acc OP d[i];
```

**🎯 它省了什么**

每处理一个元素原本要摊上一份循环开销（`i++`、`i<length` 比较、条件跳转）。展开 k 倍后这份开销被 k 个元素分摊，**减少的是指令总数里"非计算"的部分**。

**⚠️ 它没省什么——这是全节最容易错的点**

看 `combine5` 的关键路径：`acc = (acc OP d[i]) OP d[i+1]`，`acc` 依然是串行的，每次迭代两个 OP 仍首尾相接挂在同一条链上。

```
acc ──OP── (中间) ──OP── acc' ──OP── ──OP── acc'' ── ...
       ↑ 关键路径上每个元素仍贡献一个 OP 的延迟，链没断
```

实测结果（书中表 5.13）：

| 运算 | combine4 | combine5（2×1） | 延迟界限 | 吞吐量界限 |
|------|---------|----------------|---------|-----------|
| 整数 + | 1.27 | 1.01 | 1.00 | 0.50 |
| 整数 * | 3.01 | 3.01 | 3.00 | 1.00 |
| 浮点 + | 3.01 | 3.01 | 3.00 | 1.00 |
| 浮点 * | 5.01 | 5.01 | 5.00 | 0.50 |

**整数加降了（1.27→1.01）**：因为它延迟只有 1，原本瓶颈就在循环开销上，展开把开销摊薄后贴到了延迟界限。
**其余三个纹丝不动**：它们本来就贴着延迟界限，瓶颈是依赖链不是循环开销，展开对依赖链无能为力。**这证明了纯循环展开对延迟受限的运算无效。**

## 多累加器（§5.9.1）

**🎯 k×k 展开：k 个独立累加变量**

把一条链拆成 k 条互不依赖的链。2×2 的 `combine6` 用两个累加器，奇偶项分开累加：

```c
data_t acc0 = IDENT, acc1 = IDENT;
for (i = 0; i < limit; i += 2) {
    acc0 = acc0 OP d[i];       // 偶数项 → 链 0
    acc1 = acc1 OP d[i+1];     // 奇数项 → 链 1
}
for (; i < length; i++)
    acc0 = acc0 OP d[i];
*dest = acc0 OP acc1;          // 最后合并
```

**🎯 为什么这次有效**

`acc0` 和 `acc1` 两条链没有数据依赖，处理器可以**同时**把两条链的运算塞进流水线化的功能单元。原本一个乘法器干等前一个结果，现在两条链轮流喂，流水线被填满。

```
链0: acc0 ──OP── acc0' ──OP── ...
链1: acc1 ──OP── acc1' ──OP── ...     ← 两条链并行，关键路径减半
```

实测（表 5.13）：2×2 时四种运算的 CPE 大致砍半，逼近 `延迟/2`。

**🎯 要几个累加器才能饱和吞吐量界限**

关键公式：**累加器个数 k ≥ latency × capacity** 时，流水线被完全填满，CPE 触底到吞吐量界限。

- 浮点乘 latency=5、capacity=2 → 需要 `5×2=10` 个累加器才能压到 CPE=0.5
- 浮点加 latency=3、capacity=1 → 需要 3 个累加器压到 CPE=1.0

不是越多越好：超过这个数没收益，且累加器太多会**寄存器溢出**（spilling）——架构寄存器只有 16 个，编译器只好把累加器存到栈上，访存反而拖慢，CPE 回升（这是 §5.10 的上界讨论）。

**⚠️ 浮点不满足结合律——这是程序员能赢过编译器的根本原因**

多累加器改变了求和顺序：`(d0+d2+...) + (d1+d3+...)` ≠ 顺序求和。浮点加乘**不满足结合律**（舍入误差顺序相关），所以 `-O2` 编译器**默认不敢替你做**这个变换，怕改变数值结果。要让编译器自动多累加器/向量化，得显式开 `-ffast-math`（或 `-fassociative-math`），等于你授权它"可以改变浮点结合顺序"。整数加乘则满足模 2^w 结合律（溢出环绕一致），编译器更愿意做。

## 重新结合变换（§5.9.2）

**🎯 只用一个累加器，靠括号挪关键路径**

`combine7` 还是 2×1 展开，但把括号换个位置：

```c
for (i = 0; i < limit; i += 2) {
    acc = acc OP (d[i] OP d[i+1]);    // 注意括号：先算 d[i] OP d[i+1]
}
```

对比 `combine5` 的 `(acc OP d[i]) OP d[i+1]`：

- **combine5**：两个 OP 都依赖 `acc`，关键路径上每次迭代有 **2 个 OP**
- **combine7**：`d[i] OP d[i+1]` 不依赖 `acc`，可以提前算（独立运算），关键路径上每次迭代只剩 **1 个 OP**（`acc OP 结果`那个）

```
combine7 关键路径:
  acc ──OP── acc' ──OP── acc'' ...   ← 每迭代只 1 个 OP
  (d[i] OP d[i+1]) 在旁路独立算好，不占关键路径
```

**🎯 效果与多累加器相当**

只用一个累加器就把关键路径上的 OP 数减半，CPE 逼近同样的吞吐量界限。代价是同样**改变了浮点结合顺序**，编译器默认也不敢做。

**🎯 多累加器 vs 重结合**

| | 多累加器（5.9.1） | 重新结合（5.9.2） |
|---|---|---|
| 手段 | 开 k 条独立链 | 一条链上把部分运算移出关键路径 |
| 累加器数 | k 个（吃寄存器） | 1 个 |
| 逼近的界限 | 吞吐量界限 | 吞吐量界限 |
| 扩展性 | 加累加器即可，但受寄存器数限制 | 受可移出关键路径的运算数限制 |

两者本质相同——都是制造**独立的、可并行的运算**喂给流水线。工程上多累加器更直观、更常用。

## 易错点

- 循环展开（k×1）≠ 提高并行性：它只摊薄循环开销，**打不断依赖链**，对延迟受限的乘法/浮点运算 CPE 完全不变——这是最容易误以为"展开就能加速"的地方
- 真正破延迟界限的是**多累加器/重结合制造的独立依赖链**，不是展开本身；展开只是给多累加器提供"一次迭代有多个元素可分配到不同链"的载体
- 累加器不是越多越好：饱和点是 `latency × capacity`，超过没收益，再多会**寄存器溢出**导致 CPE 回升
- 浮点不满足结合律，多累加器和重结合都改变求和顺序、可能改变结果，所以 `-O2` 不会自动做，必须 `-ffast-math` 授权——这正是"手写优化能赢编译器"的根因
- 重结合只用一个累加器也能逼近吞吐量界限，别以为"没开多个累加器就没并行"——括号位置决定关键路径长度
- 整数加乘满足模 2^w 结合律（溢出环绕一致），编译器对整数更敢做这类变换

## 工程关联

- `perf stat` 观测：从 combine4→combine6，**IPC 上升**（更多独立运算并行发射）、**CPE / cycles 下降**、stalled-cycles-backend 减少
- 编译选项：`-funroll-loops` 控制展开；`-ffast-math` / `-fassociative-math` 才允许编译器自动多累加器和向量化浮点归约——数值敏感场景要谨慎开
- **SIMD 向量化本质就是多累加器思想**：一个 256-bit YMM 寄存器 4 个 double lane 各自独立累加，`-O3 -mavx2 -ffast-math` 下编译器把归约循环自动展开成多个向量累加器，是本节思想的硬件放大版
- BLAS / Eigen / 数值库的归约 kernel 几乎都是"多累加器 + SIMD + 软件流水"的手写组合，根子就在这两节
- 寄存器溢出可在汇编里直接看到：累加器太多时出现 `mov %xmmN, -off(%rsp)` 把中间值存栈，是 CPE 回升的实锤
