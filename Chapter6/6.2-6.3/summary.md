# §6.2~6.3 局部性与存储器层次结构

这两节回答 §6.1 抛出的那个问题——CPU 和主存之间几个数量级的速度鸿沟到底怎么填。答案分两步：**①程序天生有「局部性」——刚访问过的数据/指令很可能马上再被访问，相邻的数据也很可能接着被访问；②正因为有局部性，把"近期热点"放进更小更快的存储里就划算，于是 SRAM→DRAM→磁盘层层缓存，构成存储器层次结构（memory hierarchy）**。

- 局部性有两种：时间局部性（同一地址反复访问）、空间局部性（相邻地址依次访问）
- 步长为 1 的引用模式（stride-1）空间局部性最好，是写缓存友好代码的第一准则
- 取指令本身也有局部性，循环体是典型代表
- 存储器层次结构的每一层都是下一层的缓存，靠"块"为单位搬运数据
- 不命中分三类：冷不命中、冲突不命中、容量不命中——成因不同，应对手段也不同

---

## 局部性的两种形式

**🎯 时间局部性（temporal locality）**

一个被引用过的内存位置，**在不久的将来很可能被再次引用**。典型来源是循环里反复读写的变量（累加器 `sum`、循环计数器 `i`）。

**🎯 空间局部性（spatial locality）**

一个内存位置被引用后，**它附近的位置很可能在不久后被引用**。典型来源是顺序遍历数组——访问 `a[i]` 后紧接着访问 `a[i+1]`。

```c
int sum = 0;                    // sum、i 有时间局部性（每轮迭代都访问）
for (int i = 0; i < n; i++)
    sum += a[i];                // a[i] 有空间局部性（按地址顺序逐个访问）
```

**🎯 为什么硬件偏爱局部性**

存储器层次结构以「块（block）」为单位搬运数据：访问 `a[i]` 时，硬件不是只取 4 字节，而是把包含它的一整个 **cache line（典型 64 字节）**拉进 cache。如果接下来访问 `a[i+1]`，它就已经在 cache 里了——空间局部性直接转化成命中。时间局部性则保证这个块在被踢出前被反复利用。

---

## 步长与空间局部性

**🎯 步长（stride）决定空间局部性强弱**

按内存地址递增、每次跨过 k 个元素的访问叫「步长为 k 的引用模式」。**步长越小，空间局部性越好；stride-1（顺序访问）是最优**。步长一旦超过一个 cache line 能装下的元素数，每次访问都落在新块上，空间局部性彻底丢失。

**🔧 二维数组的行优先 vs 列优先**

C 语言数组按**行优先（row-major）**存储，即 `a[i][j]` 和 `a[i][j+1]` 在内存里相邻。这决定了两种遍历顺序的天壤之别：

```c
// 版本 A：行优先遍历，stride-1，空间局部性好
int sumA(int a[M][N]) {
    int sum = 0;
    for (int i = 0; i < M; i++)
        for (int j = 0; j < N; j++)
            sum += a[i][j];     // 内存里连续访问
    return sum;
}

// 版本 B：列优先遍历，stride-N，空间局部性差
int sumB(int a[M][N]) {
    int sum = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < M; i++)
            sum += a[i][j];     // 每次跳 N 个 int，几乎每访问都 miss
    return sum;
}
```

两段代码逻辑完全相同、指令数也接近，但版本 B 在大矩阵上可能慢好几倍——**这就是第 6 章最经典的"逻辑相同性能差很多"的例子，根因是 cache miss 而非指令数**。

**⚠️ 多维数组的"内层循环对应最后一维"才是 stride-1**

判断步长不能只看代码长相，要看**最内层循环变量是否对应数组的最后一个下标**。`a[i][j]` 想要 stride-1，内层必须是 `j`。这条规则推广到三维及以上同样成立。

## 取指令的局部性

**🎯 指令也存在层次结构里，也讲局部性**

程序指令存在内存中，由 CPU 取指执行，因此**取指令也服从局部性**：

- 顺序执行 → 指令的空间局部性（PC 顺序加一）
- 循环体 → 指令的时间局部性（循环体指令被反复取）

```c
for (int i = 0; i < n; i++)
    sum += a[i];   // 循环体指令很少、被执行 n 次 → 极强的指令时间局部性
```

**🎯 循环体越小，指令局部性越好**

循环体小到能整个装进 L1 指令 cache（i-cache）时，第一次迭代后取指几乎全命中。这也是为什么过度的循环展开（unrolling）有时反而变慢——展开太多会让循环体撑破 i-cache。现代 CPU 还有更靠前的 micro-op cache / loop buffer，小循环可以完全脱离取指流水线。

---

## 评价局部性的经验法则

**🎯 三条快速判断准则**

不用跑程序也能粗判一段代码局部性好坏：

- **重复引用同一变量** → 时间局部性好
- **stride-k 引用，k 越小越好**，stride-1 最佳 → 空间局部性好
- **循环体越短、迭代次数越多** → 取指局部性好

**🎯 一个对比例子**

```c
// 局部性好：stride-1
int v1(int a[N]) { int s=0; for(int i=0;i<N;i++) s+=a[i]; return s; }

// 局部性差：stride-16，跳着访问
int v2(int a[N]) { int s=0; for(int i=0;i<N;i+=16) s+=a[i]; return s; }
```

`v2` 访问的元素更少，但每次几乎都 miss；当数据集远大于 cache 时，`v2` 的**每元素耗时**反而可能高于 `v1`——这是 §6.6 "存储器山（memory mountain）"实验要量化的现象。

## 存储器层次结构：一张总图

**🎯 每一层都是下一层的缓存**

```
          快、小、贵                                慢、大、便宜
  寄存器 ─ L1 ─ L2 ─ L3 ─ 主存(DRAM) ─ 本地磁盘 ─ 远程存储(网络/分布式)
   k=0   k=1  k=2  k=3    k=4          k=5         k=6
  ↑CPU                                                    ↑容量最大
```

核心思想：**第 k 层（更快更小）充当第 k+1 层（更慢更大）的缓存**。寄存器缓存 L1，L1 缓存 L2，……，主存缓存磁盘，磁盘缓存网络。每一层只保留下一层数据的一个"热点子集"。

**🎯 靠"块"为单位在相邻层之间搬运**

相邻两层之间以固定大小的「块」传输数据，但**块大小逐层变化**：越靠近 CPU 的层，块越小、传输越快；越往下块越大，用更大的传输粒度摊薄慢介质的固定延迟。

| 层级对 | 块大小（典型） | 一次传输代价 |
|--------|---------------|--------------|
| L1 ↔ L2/L3 | 64 字节（cache line） | 几个~几十个时钟周期 |
| 主存 ↔ 磁盘 | 4 KiB（一页 page） | 毫秒级（一次缺页） |

这解释了为什么 cache 以 64 字节 line 为单位、而虚拟内存以 4 KiB 页为单位——介质越慢，越要用大块摊薄延迟。

## 缓存的核心机制：命中与不命中

**🎯 命中（hit）与不命中（miss）**

CPU 需要第 k+1 层的某个数据对象 d 时，先在第 k 层找：

- **命中**：d 已在第 k 层 → 直接用，快
- **不命中**：d 不在 → 从第 k+1 层取整个块上来（放进第 k 层），再用，慢

**🎯 不命中要"替换/驱逐"**

第 k 层已满时，取上来的新块必须覆盖一个旧块，这个被覆盖的旧块叫**牺牲块（victim block）**，挑选规则叫**替换策略（replacement policy）**，最常见是 LRU（最近最少使用）的近似实现。命中率高低很大程度取决于替换策略是否贴合程序的访问局部性。

**🎯 命中率与平均访问时间**

```
平均访问时间 = 命中率 × 命中时间 + 不命中率 × 不命中代价
```

由于相邻层速度差常达 10~100 倍，**不命中代价远高于命中时间**，所以哪怕命中率从 97% 提到 99%，平均访问时间也可能腰斩——这是缓存优化"边际收益巨大"的数学根源。

---

## 三种不命中

**🎯 冷不命中（compulsory / cold miss）**

cache 一开始是空的（冷缓存），**第一次访问任何块必然 miss**。这是不可避免的启动代价，随着程序运行（缓存暖起来）而消失，与缓存大小无关。

**🎯 冲突不命中（conflict miss）**

由于缓存的放置策略——第 k+1 层的块只能映射到第 k 层的某个（或某组）固定位置——**几个正在被交替访问的块恰好映射到同一位置，互相反复驱逐**，即使缓存整体还有空闲也照样 miss。

```c
// 典型冲突不命中：步长恰好等于缓存映射的"周期"
float dotprod(float x[8], float y[8]) {
    float sum = 0;
    for (int i = 0; i < 8; i++)
        sum += x[i] * y[i];     // 若 x、y 映射到同一 cache 组，每轮互相驱逐
    return sum;
}
```

这种"刚好踩在映射周期上"的 miss，是 §6.4 直接映射缓存里要详细分析的，也是为什么有时把数组多 padding 几个元素反而变快。

**🎯 容量不命中（capacity miss）**

程序某阶段反复访问的数据集合（**工作集，working set**）**大于缓存容量**，无论替换策略多聪明都装不下，必然持续 miss。这是唯一一种"加大缓存就能解决"的 miss，也对应 memory mountain 里"数据集超过某层容量后性能断崖下跌"的台阶。

**⚠️ 三种 miss 的区分关键**

- 冷不命中：第一次访问，跟缓存大小无关
- 冲突不命中：缓存没满也 miss，根因是放置策略 + 倒霉的地址映射
- 容量不命中：工作集 > 缓存大小，加大缓存可缓解

---

## 缓存管理：谁来管哪一层

**🎯 每一层都需要"逻辑"来管理：分块、放置、查找、驱逐**

不同层由不同主体管理，这决定了程序员能不能干预：

| 层级对 | 由谁管理 | 程序员可干预性 |
|--------|----------|----------------|
| 寄存器 ← 主存 | 编译器（寄存器分配） | 间接（写法影响编译器决策） |
| L1/L2/L3 ← 主存 | CPU 硬件（cache 控制器） | 间接（靠局部性，不能直接控制） |
| 主存 ← 磁盘（虚拟内存） | 操作系统 + MMU 硬件 | 间接（mmap/madvise 提示） |
| 本地磁盘 ← 远程 | 应用软件（如浏览器/分布式缓存） | 直接（自己写缓存逻辑） |

**🎯 对性能优化的启示**

硬件 cache 对程序员是透明的——**你无法直接命令某数据进 L1，只能通过改善代码的局部性间接提高命中率**。这正是第 6 章"缓存友好代码"的全部着力点：既然管不了缓存，就让访问模式去迎合缓存的工作方式（stride-1、控制工作集大小、避开冲突映射）。

---

## 易错点

- 局部性是程序的属性，缓存是硬件机制——**是程序先有局部性，缓存才划算**，不是缓存制造了局部性
- 空间局部性看的是「访问地址是否相邻」，不是「代码行是否相邻」；`a[i][j]` 列优先遍历代码很短，但内存上是跳着访问
- C 数组行优先，想要 stride-1 必须让**最内层循环对应最后一个下标**
- 三种 miss 别混：冷 miss 跟缓存大小无关、冲突 miss 缓存没满也发生、只有容量 miss 靠加大缓存能解
- 块大小不是全局统一的：cache 用 64 字节 line，虚拟内存用 4 KiB 页，越慢的介质块越大
- 程序员不能直接把数据塞进 L1，硬件 cache 是透明的，只能靠改善局部性间接命中
- 命中率从 97%→99% 看着只升 2 个百分点，但因不命中代价极高，平均访问时间可能减半
- 做 cache 实验前必须先**写一遍数组**：static/全局未初始化数组在被写入前整块只映射到一个物理零页（demand-zero），只读不写时 64MB 虚拟数组背后只有 4KB 物理页，反复读同一页永远全命中——测的根本不是访问模式，stride-1 和 stride-N 看不出任何差异

## 工程关联

- `perf stat -e L1-dcache-loads,L1-dcache-load-misses,LLC-loads,LLC-load-misses ./prog`：直接量化各级 cache 命中率，行优先 vs 列优先遍历同一矩阵，miss 率差距一目了然
- `perf stat -e cache-misses,cache-references`：算出 miss 率，是判断"程序卡在访存还是计算"的第一指标
- `valgrind --tool=cachegrind ./prog` 模拟 cache 行为，给出每行代码的 D1/LL miss 数，无需真实硬件计数器即可定位 cache 不友好的循环
- `lscpu` / `getconf -a | grep CACHE` 查本机各级 cache 大小和 line 大小（`LEVEL1_DCACHE_LINESIZE` 通常 64），用来估算工作集该控制在多大
- 数据库/存储引擎的"块（page）"设计、列式存储（列连续 → 扫描某列时 stride-1）都是空间局部性的工程化
- 循环分块（loop tiling / blocking）把工作集切到能放进 L1/L2 的小块，是把容量不命中转化为命中的经典手段（§6.6 矩阵乘法会用到）
- 结构体字段顺序、`alignas`/padding 调整会改变冲突不命中和 false sharing，和 §3.9 的对齐、第 12 章的并发缓存行直接相关

## 实验题

**🧪 题 1：行优先 vs 列优先遍历的 cache miss 对比**

```c
#define N 4096
static int a[N][N];

long sum_row(void) {            // stride-1
    long s = 0;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            s += a[i][j];
    return s;
}
long sum_col(void) {            // stride-N
    long s = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++)
            s += a[i][j];
    return s;
}
```

要求：

- 分别计时两个函数（`clock_gettime` 或 `perf stat` 看 wall time）
- `perf stat -e L1-dcache-load-misses,LLC-load-misses ./prog` 对比两者 miss 数
- 解释为什么 `sum_col` 的 LLC miss 远多于 `sum_row`，且数据量越大差距越夸张
- 验证：把 `N` 缩小到整个数组能装进 L2 时，两者差距是否显著缩小

**🧪 题 2：步长扫描，观察空间局部性的衰减**

```c
long sum_stride(int *a, long n, long stride) {
    long s = 0;
    for (long i = 0; i < n; i += stride)
        s += a[i];
    return s;
}
```

要求：

- 固定 `n`（如 64M 个 int），让 stride 取 1,2,4,8,16,32……
- 计算每种 stride 下的「每元素平均耗时」（总时间 ÷ 实际访问元素数）
- 画出 stride→每元素耗时 曲线，找到耗时在哪个 stride 附近跳升（应接近 `cache_line / sizeof(int)` = 16）
- 解释：stride ≥ 16 后每个 cache line 只用 1 个元素，空间局部性彻底丢失

**🧪 题 3：用 cachegrind 定位 miss 热点**

要求：

- 对题 1 的程序跑 `valgrind --tool=cachegrind ./prog`
- 看输出里 `D1mr`（L1 数据读 miss）、`DLmr`（LL miss）的总数，对比 row/col 两版
- 用 `cg_annotate` 把 miss 数标注到源码行，确认 miss 全集中在 `s += a[i][j]` 那一行
- 体会：不依赖真实 PMU 也能分析 cache 行为

**🧪 题 4：循环分块把容量不命中变成命中**

朴素矩阵乘法 `C = A × B`（N=1024）的内层对 B 的访问是 stride-N，工作集远超 cache：

```c
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        for (int k = 0; k < N; k++)
            C[i][j] += A[i][k] * B[k][j];   // B 列优先访问，容量不命中严重
```

要求：

- 实现一个分块版本（block size 取 32 或 64），让每个块的工作集能装进 L1/L2
- `perf stat -e LLC-load-misses` 对比朴素版与分块版的 miss 数和运行时间
- 解释分块如何把"容量不命中"转化为"块内反复命中"
- 调整 block size，找到本机最优值，并与 `lscpu` 给出的 L1/L2 大小对照

**🧪 题 5：验证指令局部性——循环展开的临界点**

```c
// 用宏生成展开 1/2/4/8/16/32/64 倍的累加循环
```

要求：

- 写一个简单累加循环，做不同程度的循环展开
- `perf stat -e instructions,L1-icache-load-misses ./prog` 观察展开倍数对 i-cache miss 的影响
- 找到性能拐点：展开到一定程度后，循环体撑破 L1 i-cache，i-cache miss 上升、性能回落
- 解释这就是"取指令也有局部性、循环体不能无限大"的实证
