# §6.4~6.5 高速缓存存储器与缓存友好的代码

§6.2~6.3 讲了「为什么要分层缓存」，§6.4 把镜头推到 CPU 和主存之间那一层硬件 cache 的内部，回答一个具体问题：**给定一个内存地址，cache 硬件是怎么在纳秒级里判断它命中没命中、命中又怎么取出来的**。答案是把地址拆成三段——组索引、标记、块内偏移——再围绕「组（set）× 行（line）× 块（block）」这套结构展开。直接映射、组相联、全相联只是「每组放几行（E）」的不同取值，写策略则是命中/不命中时怎么处理写操作的工程选择。§6.5 把这套机制反过来用：**理解了硬件怎么运作，就知道代码该怎么写去迎合它**——核心抓手只有三条，把循环写成 stride-1、让工作集驻留在 cache 里、把反复用的标量留在寄存器。

- cache 由 S 个组构成，每组 E 行，每行存一个 B 字节的块 + 有效位 + 标记位
- 地址被切成 `[ 标记 t | 组索引 s | 块偏移 b ]` 三段，三段长度由 (S, E, B) 唯一决定
- 直接映射（E=1）最简单但易冲突；组相联（1<E<C/B）是折中；全相联（E=C/B）无冲突但贵
- 写操作要回答两个正交问题：命中怎么写（写直达/写回）、不命中怎么写（写分配/非写分配）
- cache 参数（S、E、B）每一个都同时拉扯命中率、命中时间、不命中代价，没有免费的午餐
- 缓存友好代码两条原则：聚焦核心函数里的核心循环 + 把循环内的 miss 数压到最小；落地就是 stride-1 顺序访问 + 重复引用局部变量

## 通用 cache 的组织结构（§6.4.1）

**🎯 三个参数 (S, E, B) 定义一切**

一个 cache 由这三个数完全刻画：

| 参数 | 含义 | 关系 |
|------|------|------|
| `S` | 组（set）的个数 | `S = 2^s` |
| `E` | 每组的行（line）数，即相联度 | —— |
| `B` | 每个块（block）的字节数 | `B = 2^b` |

cache 总容量（只算数据，不含标记和有效位）：

```
C = S × E × B
```

**🎯 一行（line）里装什么**

每个 cache line 由三部分组成：

```
[ 有效位 valid | 标记 tag (t 位) | 数据块 block (B 字节) ]
```

- **有效位**：这一行有没有装着有意义的数据（cache 刚上电时全 0）
- **标记位**：用来确认这一行装的到底是不是 CPU 要找的那个块（区分映射到同一组的不同块）
- **数据块**：从下一层搬上来的 B 字节连续数据

**🎯 地址被切成三段**

CPU 给出一个 m 位物理地址，cache 硬件把它切成三段来定位：

```
  m-1                                         0
  ┌──────────────┬──────────────┬─────────────┐
  │  标记 t 位    │ 组索引 s 位   │ 块偏移 b 位  │
  └──────────────┴──────────────┴─────────────┘
       tag            set index      block offset
```

定位过程严格按这个顺序：

1. **用中间的 s 位选组**（组索引是中间段，不是高位段——这是关键设计，见易错点）
2. **在选中的组里，用高 t 位的 tag 逐行比对**，且该行有效位为 1 → 命中
3. **命中后用低 b 位的块偏移**，从 B 字节块里取出 CPU 真正要的那几个字节

```
s = log2(S)      组索引位数
b = log2(B)      块偏移位数
t = m - s - b    剩下的全是标记位
```

**⚠️ 为什么组索引取中间位而不是高位**

如果用高位选组，地址上**连续**的一大片块会全部映射到同一个组里，顺序访问（stride-1，空间局部性最好的模式）反而疯狂冲突。用中间位选组，相邻块会被打散到不同组，正好让最常见的顺序访问命中率最高。**这是「中间位索引」的全部理由——迎合空间局部性。**

## 直接映射缓存：E = 1（§6.4.2）

**🎯 每组只有一行**

直接映射（direct-mapped）是 `E=1` 的特例：每个组只有一行，所以一个内存块只能放在**唯一确定**的一个位置。定位最简单：

```
组选择：用 s 位组索引直接定位到唯一一组
行匹配：这组就一行，比 tag + 查有效位，成立就命中
字抽取：用 b 位偏移取数据
```

**🎯 命中与不命中的完整流程**

```c
// 假设 S=4 组, E=1, B=8 字节(2个int), m=... 
// 地址低 3 位是块偏移, 接着 2 位组索引, 其余是 tag
int a[8];   // a[0..7] 顺序访问
```

不命中时：从下一层取整个块上来，**覆盖**该组原来那一行（直接映射没有选择，victim 就是唯一那行），更新 tag 和有效位。

**⚠️ 直接映射的致命弱点：冲突不命中（抖动 thrashing）**

当两个**正在交替访问**的块恰好映射到同一组时，它们会反复互相驱逐，即使 cache 整体空着大半也照 miss 不误：

```c
float dotprod(float x[8], float y[8]) {
    float sum = 0.0;
    for (int i = 0; i < 8; i++)
        sum += x[i] * y[i];   // 若 x[i] 和 y[i] 映射到同一组 → 每次都互相驱逐
    return sum;
}
```

如果 `x` 和 `y` 在内存里的距离恰好是 `S×B` 的整数倍，那么 `x[i]` 和 `y[i]` 永远落进同一组，每轮迭代两次 miss，命中率惨不忍睹——**这叫抖动（thrashing）**。

**🔧 padding 解冲突**

抖动的经典修复：给数组多 padding 几个元素（如 `float x[12]` 只用前 8 个），把 `x` 和 `y` 的相对距离错开，让它们不再映射到同一组。**这就是 §6.3 说的「有时多 padding 几个元素反而变快」的原理**——代价是浪费一点空间，换 cache 不再抖动。

## 组相联缓存：1 < E < C/B（§6.4.3）

**🎯 每组放 E 行，缓解冲突**

组相联（set associative）让每组容纳 E 行（`E=2` 叫两路组相联，`E=4` 叫四路……）。一个块映射到唯一一组，但**组内可以放在任意一行**，于是映射到同一组的 E 个块可以共存，不必互相驱逐。

```
组选择：和直接映射一样，用 s 位组索引选组
行匹配：在这一组的 E 行里【并行比对】所有 tag + 有效位
字抽取：命中行用 b 位偏移取数据
```

**🎯 行匹配靠并行比较硬件**

组相联的行匹配不是逐行循环（那太慢），而是用 E 个比较器**同时**比对组内所有行的 tag。这是组相联比直接映射贵的根本原因：相联度越高，比较器越多、命中判定电路越复杂、命中时间越长。

**🎯 不命中时的替换策略**

直接映射没得选，组相联不命中时要从 E 行里挑一个 victim 替换：

- 有空行（无效行）→ 直接用空行
- 全满 → 按替换策略挑：**LRU**（最近最少使用）、LFU（最不常使用）等，硬件通常实现 LRU 的近似

替换策略只在组相联/全相联才有意义，且越复杂的策略硬件代价越高。

---

## 全相联缓存：E = C/B（§6.4.4）

**🎯 只有一个组，任意块放任意行**

全相联（fully associative）是另一个极端：`S=1`，整个 cache 就一个组，所有 `E=C/B` 行都在这组里。地址里**没有组索引位**（s=0），只剩 tag 和块偏移：

```
  ┌──────────────────────┬─────────────┐
  │      标记 t 位         │ 块偏移 b 位  │
  └──────────────────────┴─────────────┘
```

任何块可以放进任何行，彻底消除冲突不命中。

**⚠️ 为什么全相联只能做得很小**

命中判定要**并行比对全部行的 tag**——cache 有几百上千行就要几百上千个比较器，又贵又慢。所以全相联只用在「行数很少、又必须零冲突」的场合，**最典型就是 TLB（页表项缓存）**，而 L1/L2/L3 数据 cache 从不做全相联。

**🎯 三种结构是同一参数 E 的连续谱**

直接映射、组相联、全相联本质是 `E` 取不同值的同一套机制：

| 结构 | E 取值 | 冲突 | 命中判定成本 | 典型用途 |
|------|--------|------|-------------|----------|
| 直接映射 | E=1 | 多 | 最低（1 个比较器） | 早期 cache、简单场景 |
| 组相联 | 1<E<C/B | 少 | 中（E 个比较器） | 现代 L1/L2/L3（通常 4~16 路） |
| 全相联 | E=C/B | 无 | 最高（C/B 个比较器） | TLB、小型 cache |

## 写操作的处理（§6.4.5）

**🎯 写比读复杂：因为数据要往回传**

读只需要把数据搬上来，写却要解决「cache 里改了，下层的副本怎么办」的一致性问题。两个**正交**的问题：

**🎯 问题一：写命中怎么办**

- **写直达（write-through）**：每次写 cache 同时立即写下层。简单、保持一致，但每次写都吃总线带宽
- **写回（write-back）**：只写 cache，并给该行置一个**脏位（dirty bit）**；直到这个块被驱逐时才一次性写回下层。省带宽（多次写合并成一次），但电路复杂、需要脏位

**🎯 问题二：写不命中怎么办**

- **写分配（write-allocate）**：先把块从下层加载进 cache，再在 cache 里写。赌后面还会访问这个块（利用空间局部性）
- **非写分配（no-write-allocate）**：跳过 cache，直接写下层，不加载。

**🎯 两套策略的常见搭配**

现实里两两组合，最常见的是：

- **写回 + 写分配**：现代 CPU 的 L1/L2/L3 几乎都这么配，因为局部性让「写了还会再写/再读」非常普遍，合并写回省下大量带宽
- **写直达 + 非写分配**：逻辑简单，早期或对一致性要求高的场景用

**⚠️ 脏位 ≠ 有效位**

有效位说「这行有没有有意义的数据」，脏位说「这行被改过、和下层不一致、驱逐时必须写回」。写回 cache 驱逐一个干净块可以直接丢弃，驱逐脏块则必须先写回——这是写回策略额外延迟的来源。

## 缓存一致性与 false sharing（伪共享）

这是 §6.4 机制在多核场景下的一个重要副作用，正式展开在第 12 章，这里建立直觉——**false sharing 本质就是一种「逻辑上不该有、却被 cache 一致性协议强行造出来」的 cache miss**。

**🎯 多核为什么需要缓存一致性**

每个核有自己私有的 L1/L2，同一条 cache line 可能同时存在多个核的 cache 里。为保证「一个核写了，其他核别读到旧值」，硬件跑一套**缓存一致性协议（MESI 等）**：**当某个核写一条 line，其他核里这条 line 的副本必须被作废（invalidate）**。一致性的最小单位就是 §6.4 的 cache line（64 字节），不是单个变量。

**🎯 false sharing：两个核改的是不同变量，却共享同一条 line**

```c
struct {
    long a;   // 线程 0 反复写 a
    long b;   // 线程 1 反复写 b
} s;          // a 和 b 紧挨着，大概率落在同一条 64 字节 cache line
```

`a` 和 `b` 在逻辑上毫不相干，但它们处在同一条 line 上。线程 0 写 `a` → 让线程 1 缓存里这条 line 作废；线程 1 写 `b` → 又让线程 0 的副本作废……两个核来回「弹乒乓球」，每次写都变成一次跨核同步 + cache miss，明明各写各的，性能却像在抢同一个变量。

**⚠️ 它是「假」共享**

变量没有真正共享，**共享的只是承载它们的那条 cache line**——所以叫「伪（false）」共享。它不是数据竞争（结果是对的），而是纯粹的性能问题：一致性协议为了维护一条被「凑巧拼在一起」的 line，付出了大量本不必要的 line 作废和重新加载。

**🔧 解法：把热点变量错开到不同 cache line**

和直接映射抖动的 padding 思路同源——**用 padding / `alignas(64)` 把各线程独写的变量隔到不同 line**：

```c
struct {
    long a;
    char pad[64 - sizeof(long)];   // 填满一条 line，逼 b 进下一条
    long b;
} s;
// C++17 更规范：alignas(std::hardware_destructive_interference_size)
```

`perf c2c`（cache-to-cache）就是专门定位这种跨核 line 竞争的工具，第 12 章会用它做 padding 前后的对比实验。

> 📎 上面那句 `alignas(std::hardware_destructive_interference_size)` 远不止「换个规范写法」——它牵出 C++17 一对方向相反的常量、GCC 为什么默认警告你别用它、以及 cache line 到底算 64 还是 128。详见 [番外篇：hardware_destructive_interference_size](番外-hardware-interference-size.md)。

## 真实 cache 层次结构剖析（§6.4.6）

**🎯 指令 cache、数据 cache、统一 cache**

cache 不一定只存数据：

- **i-cache**：只存指令（取指用），通常只读
- **d-cache**：只存程序数据
- **统一 cache（unified）**：指令数据混存

现代 CPU 通常 **L1 分开**（L1-i + L1-d，让取指和取数据的访问不互相争用、可同时进行），**L2/L3 统一**。

**🎯 一个典型的 Intel Core i7 层次（书中例子）**

```
       每核私有                          所有核共享
  ┌─────────┐  ┌─────────┐         ┌──────────────┐
  │ L1 i-cache│  │ L1 d-cache│  →  L2  →  │   L3 cache    │  →  主存
  │  32 KB   │  │  32 KB   │  256KB        │   8 MB        │
  │  8 路    │  │  8 路    │               │              │
  └─────────┘  └─────────┘         └──────────────┘
   ~4 cycle      ~4 cycle    ~10 cycle      ~40-75 cycle    ~hundreds
```

越往下：容量越大、相联度越高、延迟越大、越多核共享。block 大小各级都是 64 字节。

**🔧 在自己机器上验证**

`lscpu`、`getconf -a | grep CACHE`、`/sys/devices/system/cpu/cpu0/cache/index*/` 都能看到本机各级 cache 的大小、相联度（`ways_of_associativity`）、line 大小（`coherency_line_size`），和书里的图一一对上。

## cache 参数的性能权衡（§6.4.7）

**🎯 每个参数都是双刃剑**

| 调大谁 | 好处 | 代价 |
|--------|------|------|
| **块大小 B ↑** | 利用空间局部性，一次拉更多有用数据 | 行数变少 → 时间局部性变差；不命中代价（传输时间）变大 |
| **相联度 E ↑** | 冲突不命中减少，抖动概率降低 | 比较器多 → 命中时间增加、电路贵、替换逻辑复杂 |
| **cache 容量 C ↑** | 命中率提高（容量不命中减少） | 更慢、更贵、更耗电；命中时间可能上升 |

**🎯 命中时间 vs 不命中代价的拉扯**

为什么 L1 小而 L2/L3 大？因为 L1 追求**最短命中时间**（在关键路径上，每次访存都要过），只能做小、相联度适中；越往下越追求**高命中率**来摊薄昂贵的下层访问，所以做大、相联度更高，命中时间慢一点也认了。**整个层次结构就是「命中时间」和「命中率」在不同层做不同取舍的产物。**

**⚠️ 不命中代价远大于命中时间，所以优先保命中率**

```
平均访问时间 = 命中时间 + 不命中率 × 不命中代价
```

由于不命中代价（去下层取，几十到几百周期）远高于命中时间（几周期），**降低不命中率的收益通常压倒一切**。这也是为什么写「缓存友好代码」（改善局部性、控制工作集、避开冲突映射）是性能优化的重头戏——下面 §6.5 就把这件事讲透。

## 编写缓存友好的代码（§6.5）

前面都在讲 cache 硬件「怎么运作」，§6.5 把视角翻过来：**程序员手里能拨动的旋钮是什么**。结论很朴素——局部性好的代码 cache miss 少、跑得快，而局部性几乎完全由「内存引用模式」决定，这是源码层面就能控制的东西。

**🎯 两条基本原则**

1. **让最常见的情况运行得快**：程序往往把绝大部分时间花在少数核心函数里，这些函数又把绝大部分时间花在少数循环上。优化精力要砸在这些核心循环，而不是均摊到全部代码
2. **每个循环内部尽量减小 cache 不命中数量**：在其他条件（计算量、访存总量）相同时，命中率更高的循环就是更快的循环

**🎯 两种局部性各自的代码抓手**

- **时间局部性 → 重复引用局部变量**：像 `sum`、循环下标 `i` 这种被反复读写的标量，编译器会把它放进寄存器，访问零延迟。写代码时主动用局部变量缓存「会被多次用到的值」，就是在制造时间局部性
- **空间局部性 → stride-1 顺序访问**：步长（stride）越小，单位时间踩进的新 cache line 越少，miss 率越低。stride-1（顺序）是空间局部性的理想形态；步长一旦大到「每次访问都跳进新的一条 line」，空间局部性就彻底丧失

**🎯 miss 率怎么定量算（stride-1 的命中规律）**

stride-1 遍历一个数组时，每跨进一条新的 cache line 触发 1 次 cold miss，这条 line 内剩下的元素全部命中。于是：

```
stride-1 的 miss 率 = 单个元素大小 / 一条 cache line 大小
```

```c
int sumvec(int v[N]) {
    int i, sum = 0;            // sum、i 在寄存器 → 时间局部性
    for (i = 0; i < N; i++)
        sum += v[i];           // v[i] stride-1 → 空间局部性
    return sum;
}
```

`int` 占 4 字节、line 64 字节 → 一条 line 装 16 个 int → 每 16 次访问只有第 1 次 miss → **miss 率 = 4/64 = 1/16 ≈ 6.25%**。CSAPP 原文按 block=32 字节算得 1/8，换算关系一样——**关键不是具体数字，而是「stride-1 把 miss 摊到了一整条 line 上」这个事实**。

**🔧 行优先 vs 列优先：同样的计算，miss 率差一个数量级**

C 语言的二维数组是**行优先（row-major）**存储：`a[i][j]` 和 `a[i][j+1]` 在内存里相邻，`a[i][j]` 和 `a[i+1][j]` 隔了一整行。于是遍历顺序直接决定 stride：

```c
// 行优先遍历：内层走 j → stride-1，缓存友好
int sumarrayrows(int a[M][N]) {
    int i, j, sum = 0;
    for (i = 0; i < M; i++)
        for (j = 0; j < N; j++)
            sum += a[i][j];        // 顺着内存走 → miss 率 = 元素/line = 1/16
    return sum;
}

// 列优先遍历：内层走 i → stride-N，缓存灾难
int sumarraycols(int a[M][N]) {
    int i, j, sum = 0;
    for (j = 0; j < N; j++)
        for (i = 0; i < M; i++)
            sum += a[i][j];        // 每次跳一整行 → 步步踩新 line
    return sum;
}
```

`sumarraycols` 每次访问 `a[i][j]` 都跳 `N` 个元素，落进一条全新的 line；当数组大于 cache 时，等内层下一轮回到这条 line，它早被驱逐了——**miss 率逼近 100%，是行优先的 16 倍**。两个函数计算量、访存次数完全相同，唯一差别是引用顺序，性能却差一个数量级。**这正是 §6.2~6.3 矩阵行/列遍历 perf 实验背后的机制级解释。**

**⚠️ 缓存友好 ≠ 减少访存次数**

`sumarrayrows` 和 `sumarraycols` 访存次数一模一样，快慢只取决于「这些访存能不能命中」。优化局部性不是少读内存，而是**让读内存尽量落在已经搬上来的 line 内**——是「同样的活儿换个顺序干」，不是「少干活」。

## 易错点

- 组索引用的是地址的**中间位**不是高位——高位索引会让顺序访问全挤进一个组，中间位才能把相邻块打散、迎合空间局部性
- 直接映射 ≠ cache 小，它是 `E=1` 的相联度，问题是冲突/抖动而非容量；冲突不命中在 cache 没满时照样发生
- 抖动的根因是两个交替访问的块映射到同一组，距离恰为 `S×B` 倍数，padding 错开距离即可解
- 全相联不是「更高级所以更好」，它因为要并行比对所有行只能做得极小，L1/L2/L3 从不用全相联，TLB 才用
- 写命中策略（写直达/写回）和写不命中策略（写分配/非写分配）是**两个正交问题**，别混成一个
- 脏位和有效位是两回事：有效位管「有没有数据」，脏位管「改没改过、驱逐时要不要写回」
- 块越大未必越好——块变大行数变少，时间局部性变差，且单次不命中传输更慢
- false sharing 不是数据竞争（结果是对的），是纯性能问题；共享的不是变量而是承载它们的同一条 cache line，靠 padding/`alignas(64)` 隔开即可
- `C = S × E × B` 只算数据容量，标记位和有效位的开销不计入但真实存在
- 缓存友好 ≠ 减少访存：行优先和列优先访存次数完全一样，差别只在「这些访存能不能命中」，优化的是引用顺序不是访存总量
- stride-1 的 miss 率是「元素大小 / line 大小」（如 4B int + 64B line = 1/16），不是固定 25%——书里的 1/8 是按 32B block 算的，换 line 大小数字就变
- C 数组是行优先存储，所以「内层循环走最右那一维下标」才是 stride-1；二维数组把内外层循环写反，就是从 1/16 miss 率掉到接近 100% 的根源
- 在 Intel 大小核（hybrid）CPU 上，`perf stat -e L1-dcache-load-misses` 会三行全空——E-core/LP E-core 的 PMU 不支持该别名（`<not supported>`），P-core 又因程序太短没被调度到（`<not counted>`）；正确姿势是 `perf stat -e cpu_core/L1-dcache-load-misses/ taskset -c 0 ./prog`，显式选 P-core 事件并绑核
- **顺序访问（stride-1）下 `L1-dcache-load-misses` 测不出工作集超缓存的效应**——硬件预取器会在 demand load 之前把数据搬进 L1，miss 绝对数恒定在冷启动量级，miss 率反被撑大的分母稀释（实测 32KB→64MB 工作集 miss 率不升反降）；要暴露各级缓存延迟必须用**随机访问/指针追逐**打败预取器，延迟阶梯才会显现（实测 L1≈4、L2≈14、L3≈40、DRAM≈300+ cycle）

## 工程关联

- `getconf -a | grep CACHE` / `lscpu` / `cat /sys/devices/system/cpu/cpu0/cache/index*/{size,ways_of_associativity,coherency_line_size}`：读出本机 (S, E, B)，反算 s/b/t 位数，把书里的抽象对到自己 CPU
- `perf stat -e L1-dcache-loads,L1-dcache-load-misses,LLC-loads,LLC-load-misses ./prog`：分级看命中率，定位瓶颈卡在哪一层
- `perf c2c`（cache-to-cache）：定位多核间的缓存行竞争，是第 12 章 false sharing 的直接观测工具——false sharing 本质就是两个核反复写同一条 64 字节 line 触发 cache 一致性写回
- `valgrind --tool=cachegrind`：用 `--D1=size,assoc,linesize` 参数模拟任意 (C, E, B) 配置，不用换硬件就能研究相联度/块大小对 miss 的影响
- 数组 padding、`alignas(64)`、结构体字段重排都是在「错开冲突映射」或「让热字段共享 cache line」——和直接映射的抖动、写回的脏行驱逐直接相关
- 写回 + 写分配是现代 CPU 默认，理解它才能解释「为什么大量小写操作不会立刻打满内存带宽」——它们在 L1 里被合并了
- TLB 是全相联 cache 的现实身影（§9.6），理解全相联为何只能小，就懂了 TLB 为何只有几十上百项
- 循环交换（loop interchange）把列优先改成行优先、循环分块（blocking/tiling）把大工作集切成驻留 cache 的小块——都是 §6.5「stride-1 + 控制工作集」原则的落地，第 5 章优化矩阵乘法时会正式用上
- `gcc -O3 -ftree-loop-interchange` 等优化在简单循环上能自动帮你把 stride 改小，但遇到指针别名、复杂下标就放弃——所以缓存友好的访问顺序仍要程序员主动写对，不能全指望编译器

## 实验题

**🧪 题 1：手算地址拆分**

给定 cache：`C = 1 KB`，`B = 16 字节`，直接映射（`E=1`），地址 `m = 16` 位。

要求：

- 算出 `S`、`s`、`b`、`t` 各是多少（应得 S=64, b=4, s=6, t=6）
- 对地址 `0x1834`、`0x1835`、`0x0F34`，分别拆出 tag/组索引/块偏移
- 判断 `0x1834` 和 `0x0F34` 是否映射到同一组，会不会互相冲突
- 把 `E` 改成 2 路组相联（C 和 B 不变），重新算 s/b/t，体会相联度如何改变拆分

**🧪 题 2：复现直接映射的抖动**

```c
#define N (1 << 12)        // 让 stride 恰好等于 cache 一路的大小
float x[N], y[N];

double dotprod(void) {
    double sum = 0;
    for (int i = 0; i < N; i++)
        sum += x[i] * y[i];
    return sum;
}
```

要求：

- 调整 `x`、`y` 的相对地址（用一个全局 padding 数组挤开它们），让它们的距离恰好落在「映射到同一组」的位置
- `perf stat -e L1-dcache-load-misses ./prog` 对比「冲突布局」和「错开布局（padding 后）」的 miss 数
- 验证：padding 几个 float 错开后，miss 数显著下降，运行时间变快
- 解释为什么 cache 明明没满，冲突布局却疯狂 miss

**🧪 题 3：相联度对 miss 的影响（cachegrind 模拟）**

要求：

- 拿题 2 的程序，用 `valgrind --tool=cachegrind --D1=32768,1,64`（1 路=直接映射）跑一遍
- 改成 `--D1=32768,8,64`（8 路），同样的程序、同样的容量和 line，只改相联度
- 对比两次 `D1mr`（L1 数据读 miss）数量
- 解释：容量和块大小都没变，仅提高相联度为什么能把抖动型 miss 压下去

**🧪 题 4：块大小的双刃剑**

要求：

- 用 cachegrind 的 `--D1=8192,2,B` 固定容量和相联度，让 `B` 取 16/32/64/128
- 对一个 stride-1 的顺序遍历，看 miss 数随 B 增大如何下降（空间局部性被更大块利用）
- 再对一个随机访问（stride 很大）的模式，看 B 增大时 miss 数是否反而不降甚至变差
- 解释：为什么顺序访问偏爱大块，而随机访问下大块只是浪费传输带宽

**🧪 题 5：观察写回策略的效果**

```c
// 对同一块内存反复写，观察是否立刻打满内存带宽
#define M (64 * 1024 * 1024)
char buf[M];

void hammer(void) {
    for (int rep = 0; rep < 100; rep++)
        for (long i = 0; i < M; i += 64)   // 每条 cache line 写一次
            buf[i]++;                       // 读-改-写
}
```

要求：

- `perf stat -e cache-references,cache-misses,L1-dcache-stores ./prog` 观察写操作的命中情况
- 把工作集 `M` 调到小于 L1/L2 容量，对比写操作是否几乎全在 cache 里完成（写回合并）
- 解释：写回 + 写分配下，反复写同一小块为什么不会持续打总线，而写直达会
- 把内层步长改成 1（每字节都写）和 64（每 line 写一次），对比 store miss 的差异

**🧪 题 6：行优先 vs 列优先（§6.5 核心实验）**

```c
#define N 4096
int a[N][N];

long sum_rows(void) {          // 内层走 j → stride-1
    long sum = 0;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            sum += a[i][j];
    return sum;
}

long sum_cols(void) {          // 内层走 i → stride-N
    long sum = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++)
            sum += a[i][j];
    return sum;
}
```

要求：

- 用 `perf stat -e cpu_core/L1-dcache-loads/,cpu_core/L1-dcache-load-misses/ taskset -c 0 ./prog` 分别测两个函数（绑 P-core，理由见易错点最后两条）
- 验证 `sum_rows` 的 L1 miss 率接近 `4/64 = 1/16`，`sum_cols` 接近 100%，比值约 16 倍
- 对比两者墙钟时间，确认计算量相同但 `sum_cols` 慢一个数量级
- 思考：把 `N` 缩小到整个 `a` 能塞进 L2/L3 时，列优先的劣势会不会缩小？为什么

**🧪 题 7：stride 扫描，画出空间局部性的衰减曲线**

```c
long stride_sum(int *arr, long n, long stride) {
    long sum = 0;
    for (long i = 0; i < n; i += stride)
        sum += arr[i];
    return sum;
}
```

要求：

- 固定数组远大于 L3（如 256 MB），让 `stride` 取 1,2,4,8,16,32（单位：int）
- 用 perf 测每个 stride 的 L1 miss 率，确认 stride 从 1 涨到 16（= 64B/4B，跨满一条 line）时 miss 率从 1/16 一路升到 ~100%，之后趋于饱和
- 解释：为什么 miss 率在 stride=16 处「封顶」而不是无限上升——一旦每次访问都踩新 line，空间局部性已耗尽，再大的步长也不会更差（只会因预取失效略有波动）
