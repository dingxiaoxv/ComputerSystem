# §8.1 异常

本节是整个「异常控制流」（ECF）的硬件起点。前面章节里，程序计数器的变化要么是顺序执行（`pc + 指令长度`），要么是显式的跳转/调用/返回——这些都是程序「自己」决定的平滑流。但真实系统里，处理器还必须响应那些**和当前指令流无关的状态变化**：定时器到点、磁盘数据就绪、除以了 0、访问了非法地址。异常（exception）就是硬件层面对这些突变的统一应答机制——它是上层「`fork`、进程切换、信号、`try/catch`」这一整套 ECF 的最底层地基。看懂这一节，才能理解为什么一次普通的内存访问也可能「凭空」陷入内核。

## 异常是控制流的突变

🎯 **定义**：异常是为响应某个**处理器状态变化**而做的控制流突变（an abrupt change in the control flow），这个状态变化称为**事件**（event）。事件可能和当前执行的指令直接相关（如除零、缺页），也可能完全无关（如定时器中断、网卡收到数据包）。

🎯 **基本流程**：处理器正在执行当前指令 `I_curr`，检测到事件发生 → 通过**异常表**间接跳转到对应的**异常处理程序**（exception handler，一段内核代码）→ 处理完后，根据异常类型回到 `I_curr`、`I_next` 或直接终止程序。

```
        应用程序                       异常处理程序（内核）
   ...                          ┌──> handler 代码
   I_curr  ──事件发生──┐         │     ...
   I_next            └──异常──> ─┘     处理事件
   ...               <──返回(可选)──   (1) 返回 I_curr
                                       (2) 返回 I_next
                                       (3) abort
```

🎯 **和普通跳转的本质区别**：`call`/`jmp`/`ret` 是程序在用户态自己改 PC；异常则是**硬件 + 内核**接管控制权，往往伴随用户态→内核态的切换。一条看似人畜无害的 `movq (%rax), %rbx` 可能因为 `%rax` 指向未映射的页而触发缺页异常，凭空陷入内核——这是用 C 代码完全看不出来的「隐藏控制流」。

## 异常表与异常号

🎯 **异常号（exception number）**：每种异常被分配一个唯一的非负整数。一部分由处理器设计者定义（除零、缺页、内存访问违例、断点），另一部分由内核开发者定义（系统调用、外部 I/O 设备信号）。

🎯 **异常表（exception table）**：系统启动时内核分配并初始化的一张跳转表，表项 `k` 存放第 `k` 号异常处理程序的入口地址。它的角色相当于「中断向量表」。

🔧 **地址计算**：异常表基址存放在专用的**异常表基址寄存器**（exception table base register）。给定异常号 `k`，处理程序地址 = `*(base + k × 字长)`。x86-64 上这张表就是 **IDT**（Interrupt Descriptor Table），基址寄存器是 `IDTR`，用 `lidt` 指令加载——这是内核启动早期必做的事。

```
异常表基址寄存器 ──> ┌─────────────┐  表项 0：除零 handler 地址
                    │  entry 0    │
                    ├─────────────┤  表项 1：调试 handler 地址
   异常号 k ───────>│  entry k    │──> handler_k 入口
                    ├─────────────┤
                    │   ...       │
                    └─────────────┘
```

## 异常处理与过程调用的差异

🎯 **表面相似**：异常处理像一次「过程调用」——都要保存返回地址、跳到一段代码、执行完再回来。但底层差别很大，理解这些差别是看懂上下文切换（§8.2）的前提。

⚠️ **四个关键不同点**：

- **返回地址的选择**：普通 `call` 总是压入下一条指令地址；异常根据类型，压入的可能是**当前指令**（故障要重试）或**下一条指令**（陷阱已完成）。
- **保存的状态更多**：除了返回地址，处理器还会把一些额外的处理器状态（如条件码寄存器 `EFLAGS`）压栈，返回时一并恢复——处理程序不能破坏被中断程序的执行环境。
- **栈的切换**：当从用户态切到内核态时，这些状态被压到**内核栈**而非用户栈，因为内核不信任用户栈。
- **特权级提升**：处理程序运行在**内核模式**，拥有对所有系统资源的完全访问权。

## 异常的四种类别

这是本节的考点核心。按「触发原因」和「返回行为」两个维度，异常分成四类：

🎯 **中断（Interrupt）—— 异步**：
- 来源：处理器**外部** I/O 设备的信号（时钟、网卡、键盘、磁盘）。
- 异步：和当前执行的任何指令都无关，随时可能发生。
- 返回：总是返回到**下一条**指令 `I_next`，对程序透明。
- 机制：设备给处理器的中断引脚发信号，把异常号放到系统总线上；当前指令执行**完**后才响应。

🎯 **陷阱（Trap）—— 同步、有意**：
- 来源：执行某条指令**有意**触发，最重要的用途是**系统调用**。
- 返回：返回到**下一条**指令 `I_next`。
- 机制：用户态执行 `syscall` 指令陷入内核，提供一个像过程调用一样的「系统调用」接口。

🎯 **故障（Fault）—— 同步、可恢复**：
- 来源：执行指令时遇到可能可纠正的错误。典型代表是**缺页故障**（page fault）。
- 返回：如果 handler 能修复（如把缺失的页从磁盘调入内存），就**重新执行**触发故障的**当前**指令 `I_curr`；否则调用 `abort` 终止。
- 关键：故障的「重试」语义正是按需分页（demand paging）和写时复制（COW）能工作的根本。

🎯 **终止（Abort）—— 同步、不可恢复**：
- 来源：不可恢复的致命错误，典型是硬件错误（如 DRAM/SRAM 奇偶校验、ECC 不可纠正）。
- 返回：**不返回**，直接把控制交给 `abort` 例程，终止程序。

⚠️ **同步 vs 异步**是第一刀：中断是异步（外部、和指令无关），其余三类都是同步（由执行某条指令直接引起，称为这条指令的「故障指令」faulting instruction）。

## 三种返回行为速记

把四类异常压缩成「返回到哪」这一个问题，最容易记牢：

| 类别 | 同步/异步 | 返回行为 |
|------|-----------|----------|
| 中断 Interrupt | 异步 | 返回 `I_next`（透明） |
| 陷阱 Trap | 同步 | 返回 `I_next` |
| 故障 Fault | 同步 | 重试 `I_curr` 或 abort |
| 终止 Abort | 同步 | 不返回 |

🎯 一句话区分陷阱和故障：陷阱「我故意的，办完接着往下走」，故障「我出错了，修好了再来一遍」。

## 易错点

- 不要以为「异常 = 程序出错」：陷阱（系统调用）是**主动、正常**的控制流转移，每次 `read`/`write`/`open` 都在用它，和「错误」无关。
- 不要把中断当成由指令引起：中断是**异步**的，由外部设备引起，和「当前执行哪条指令」毫无关系；故障/陷阱/终止才是指令引起的同步事件。
- 故障不一定意味着崩溃：缺页是最常见的故障，handler 修复后会**重新执行**原指令，程序毫无察觉——只有修不好（如访问真正非法的地址）才升级为段错误。
- 「返回到当前指令」是故障专属：陷阱和中断都返回**下一条**指令，只有故障可能返回**触发它的那一条**，因为它要重试。
- 异常表 ≠ switch 的跳转表：异常表索引是「异常号」，由硬件/内核约定；它在内核态、用启动时初始化的专用基址寄存器寻址，不是编译器生成的用户态数据。
- 异常处理程序运行在内核态，不是用户态函数：它能访问全部资源，且通常用内核栈，普通 `gdb` 单步进不去。

## 工程关联

- **系统调用的真身**：x86-64 Linux 上，`syscall` 指令触发陷阱，系统调用号放 `%rax`，参数依次放 `%rdi,%rsi,%rdx,%r10,%r8,%r9`（注意第 4 个参数是 `%r10` 而非过程调用约定的 `%rcx`）。`strace ./a.out` 能把这些陷阱逐条打印出来。
- **缺页是性能与功能的双刃**：`perf stat -e faults,minor-faults,major-faults ./a.out` 能看到 minor fault（页已在内存，只需建映射，如首次访问 `malloc` 的堆页、COW）和 major fault（要从磁盘/swap 读，开销大几个数量级）。大量 major fault 通常意味着内存不足在抖动。
- **段错误（SIGSEGV）的来路**：用户访问非法地址 → 硬件触发缺页故障 → 内核 handler 发现该地址不在合法 VMA 内、无法修复 → 通过信号机制给进程发 `SIGSEGV`。可见「故障」是底层硬件机制，「信号」是内核暴露给用户的上层抽象（详见 §8.5）。
- **IDT 与内核启动**：Linux 启动时 `idt_setup_traps()` 填充 IDT，把 0~31 号设为 CPU 异常（如 0 号 `#DE` 除零、13 号 `#GP` 通用保护、14 号 `#PF` 缺页），32 号以上留给外部中断；`lidt` 把 IDTR 指向这张表。
- **时钟中断驱动调度**：内核靠周期性时钟中断（一种异步中断）夺回 CPU 控制权，才能做抢占式调度——没有中断，一个死循环用户程序就能霸占 CPU。这正是「逻辑控制流」（§8.2）能交错运行的物理基础。

## 实验题

**🧪 题 1：用本目录 main.c 观察故障（除零）**

本目录 `main.c` 就是一个最小的故障触发器：

```c
#include <stdio.h>
int main() {
    int x = 1 / 0;       // 整数除零 → #DE 故障 → SIGFPE
    printf("%d\n", x);
    return 0;
}
```

要求：
- `gcc -O0 -g -o prog main.c`（会有编译告警，可忽略）运行，确认收到 `Floating point exception (core dumped)`——尽管是整数除法，信号名却是 `SIGFPE`。
- `gdb ./prog` 里 `run`，崩溃时 `info registers rip` 看 PC 停在 `idivl` 那条指令——验证「故障返回到当前指令」（崩溃指令就是触发故障的那条）。
- 用 `objdump -d prog | grep -A3 idiv` 找到那条除法指令，理解 0 号异常 `#DE` 是怎么产生的。
- 结论：除零是同步、不可在用户态恢复的故障，内核最终通过 `SIGFPE` 终止进程。

**🧪 题 2：用 strace 观察陷阱（系统调用）**

```c
#include <unistd.h>
int main(void) {
    write(1, "hi\n", 3);   // 一次有意触发的陷阱
    return 0;
}
```

要求：
- `gcc -O0 -o trap trap.c`，然后 `strace ./trap`。
- 观察输出里的 `write(1, "hi\n", 3) = 3`，理解这一行就是一次「陷阱异常 → 系统调用 → 返回 I_next」。
- `objdump -d trap` 看 `write` 最终如何走到 `syscall` 指令。
- 结论：陷阱是同步、主动、返回下一条指令的异常。

**🧪 题 3：观察异步中断的存在**

要求：
- 运行 `cat /proc/interrupts`，观察各 CPU 上的中断计数（`LOC` 本地 APIC 定时器、网卡、磁盘等）。
- 跑一个纯计算死循环 `while(1);`，每隔一秒再看一次 `/proc/interrupts`，观察定时器中断（`LOC`）持续增长。
- 结论：即使程序本身不做任何 I/O，定时器中断也在异步地、和指令无关地持续打断它，这是抢占式调度的基础。
