# §8.2 进程

§8.1 讲的是硬件层面的异常——那是底层砖石。本节登上一层，回答一个更哲学的问题：**操作系统用这些异常机制，给每个程序编织了什么样的「假象」？** 答案是「进程」。进程是计算机科学最深刻、最成功的抽象之一：它让每个程序都觉得自己**独占整个 CPU**（逻辑控制流），并且**独占整个内存**（私有地址空间）。这两个假象，配合「用户/内核模式」的隔离和「上下文切换」的机制，构成了现代多任务系统的运行模型。理解了进程，才能理解为什么 `fork` 出来的两个进程互不干扰、为什么一个进程崩了不会拖垮别人、以及 `top` 里几百个进程是怎么「同时」跑在 8 个核上的。

## 进程提供的两个核心假象

🎯 **定义**：进程是一个**正在执行的程序的实例**（an instance of a program in execution）。系统里的每个程序都运行在某个进程的上下文中。上下文（context）= 程序正确运行所需的全部状态，包括内存中的代码与数据、栈、通用寄存器、PC、环境变量、打开的文件描述符集合。

🎯 **假象一：独立的逻辑控制流**——每个进程都好像独占地使用处理器。
🎯 **假象二：私有的地址空间**——每个进程都好像独占地使用内存系统。

🔧 这两个假象不是免费的，它们由 OS **内核**用两套机制提供：逻辑控制流靠**异常控制流 + 上下文切换**实现，私有地址空间靠**虚拟内存**（第 9 章）实现。本节先把这两个假象讲透。

## 逻辑控制流

🎯 **概念**：如果用调试器单步跟踪一个进程，会看到一系列 PC 值，它们唯一对应着程序指令或共享库/内核代码中的指令——这个 PC 值的序列就叫**逻辑控制流**（logical control flow），简称逻辑流。每个进程都有自己的一条逻辑流。

🎯 **物理真相 vs 逻辑假象**：物理上，多个进程**轮流**使用一个 CPU，每个进程执行一段后被内核**抢占**（暂时挂起），换另一个进程跑。但从单个进程的视角看，它的逻辑流是**连续不断**的——它感觉不到自己被打断过，仿佛独占 CPU。

```
物理时间轴（一个 CPU）：
  进程 A: ███····███····███       (····表示被挂起的时间段)
  进程 B: ···███·······███··
  进程 C: ······███·███·····

每个进程「看到」的逻辑流都是连续的 ███████
```

## 并发流与并行流

🎯 **并发（concurrency）**：一个逻辑流在时间上和另一个逻辑流**有重叠**（overlap），就称它们并发运行，互为并发流。注意——并发**不要求多核**，关键是「时间段重叠」。上图中 A 和 B 并发，A 和 C 也并发。

🎯 **多任务（multitasking / time slicing）**：一个进程和其他进程轮流运行的概念叫多任务，进程执行其逻辑流的每一段时间叫**时间片**（time slice）。

🎯 **并行（parallelism）—— 并发的真子集**：如果两个流**并发地运行在不同的处理器核（或不同计算机）上**，称它们并行运行。并行流是并发流的特例。

⚠️ **关键区分**：
- 并发 = 时间上重叠（单核靠时间片轮转就能做到，是「看起来同时」）。
- 并行 = 物理上真的同时（必须有多个执行单元，是「真的同时」）。
- 所有并行流都是并发流，但并发流不一定并行。这对概念在第 12 章并发编程里反复出现。

## 私有地址空间

🎯 **概念**：进程为每个程序提供它自己的**私有地址空间**。这块空间里某个地址对应的内存字节，一般不能被其他进程读写——从这个意义上说，地址空间是私有的。

🎯 **统一的空间布局**：尽管每个私有地址空间的内容不同，但它们的**总体结构是一致的**（这正是统一抽象的威力）。x86-64 Linux 进程地址空间自底向上：

```
   高地址  ┌──────────────────────┐
           │  内核虚拟内存          │  对用户代码不可见
           ├──────────────────────┤  ← %rsp (栈顶)
           │  用户栈 (向下增长)      │
           │        ↓             │
           │                      │
           │        ↑             │
           │  共享库内存映射区域     │  (如 libc.so via mmap)
           │                      │
           │        ↑             │
           │  运行时堆 (向上增长)    │  ← malloc / brk
           ├──────────────────────┤
           │  读写数据段 (.data/.bss)│
           │  只读代码/数据段        │  ← 从可执行文件加载
   低地址  └──────────────────────┘  0x400000 起 (典型)
```

🔧 关键在于：**每个进程都看到同样的地址布局**（比如代码段都从 `0x400000` 附近开始），但这些相同的虚拟地址在物理内存里被映射到完全不同的物理页——这就是「私有」的来源，由虚拟内存（第 9 章）实现。

## 用户模式与内核模式

🎯 **为什么需要两种模式**：要实现进程隔离，处理器必须能限制应用程序能执行的指令和能访问的地址范围。处理器用某个**控制寄存器中的一个模式位**（mode bit）来描述当前进程享有的特权。

🎯 **内核模式（kernel mode / 超级用户模式）**：模式位置位时，进程运行在内核模式，可以**执行指令集中的任何指令**，访问系统中**任何**内存位置。

🎯 **用户模式（user mode）**：模式位未置位时，进程运行在用户模式：
- **不允许**执行特权指令（halt、改模式位、发起 I/O、加载/存储 IDTR 等）。
- **不允许**直接引用内核区的代码和数据，否则触发保护故障。
- 要访问内核代码和数据，只能**间接**地通过系统调用接口。

🎯 **模式切换的唯一入口是异常**：进程一开始在用户模式。要变为内核模式，唯一途径是**异常**——中断、故障或陷阱（系统调用）。异常发生时控制传给异常处理程序，处理器把模式从用户切到内核；处理程序返回时，又切回用户模式。

🔧 **/proc 文件系统**：Linux 通过 `/proc` 把内核数据结构以文件形式暴露给用户程序，让用户态能（只读地）查看内核状态——`/proc/<pid>/maps` 看进程地址空间映射、`/proc/cpuinfo` 看 CPU、`/proc/<pid>/status` 看进程状态。这是「用户态通过受控接口窥探内核」的典型设计。

## 上下文切换

🎯 **定义**：内核为每个进程维护一个**上下文**（context），即重启该进程所需的状态——通用寄存器、浮点寄存器、PC、用户栈、状态寄存器、内核栈，以及描述地址空间的页表、当前进程信息表、打开文件表等内核数据结构。

🎯 **上下文切换（context switch）三步**：内核通过这种叫上下文切换的高层异常控制流来实现多任务：
1. **保存**当前进程的上下文（寄存器等存入内核数据结构）。
2. **恢复**某个先前被抢占的进程的上下文。
3. 将控制**传递**给这个新恢复的进程。

🎯 **何时发生**：
- 内核代表用户执行系统调用时，**可能**发生切换。例如 `read`/`sleep` 等会阻塞的系统调用，内核会切到别的进程而不是干等。
- **中断**也会触发切换，最典型是**定时器中断**：每隔几毫秒触发一次，内核借此判断当前进程是否已运行足够久，若是则抢占它、切到下一个就绪进程。

```
进程 A (用户态)
  │  read(...)  ── 陷阱 → 内核态
  │              内核发现 read 要等磁盘，发起 DMA
  │     ┌── 上下文切换：保存 A，恢复 B
  ▼     ▼
进程 B (用户态) 运行...
        │  ◄── 磁盘中断：数据就绪
        │     ┌── 上下文切换：保存 B，恢复 A
        ▼     ▼
进程 A 从 read 返回 (用户态) 继续
```

⚠️ 上下文切换发生在**内核态**，由内核的调度器（scheduler）决定切给谁。它本质上是「§8.1 的异常机制」之上构建的高层 ECF——异常是机制，上下文切换是策略的载体。

## 易错点

- 并发 ≠ 并行：并发只要求逻辑流时间重叠，单核时间片轮转就算并发；并行要求物理上多核同时执行。「我电脑单核也能跑多个程序」靠的是并发，不是并行。
- 进程 ≠ 程序：程序是磁盘上静止的字节（可执行文件），进程是「程序的一次执行实例」，自带运行时状态（寄存器、栈、PC）。同一个程序可以同时有多个进程实例。
- 「私有地址空间」不是说物理内存私有，而是虚拟地址私有：不同进程的同一个虚拟地址 `0x400000` 映射到不同物理页；私有性由虚拟内存的地址翻译保证，不是地址数值不同。
- 进程不能「自己」进内核模式：用户态程序无法靠一条普通指令把自己提权，唯一进内核的路是触发异常（系统调用/故障/中断），且进去后跑的是内核代码而非用户代码。
- 上下文切换不只是换寄存器：还要切换页表（地址空间）、刷新 TLB 等，开销不小（微秒级），这正是「线程比进程轻」的原因之一（线程共享地址空间，切换无需换页表）。
- 时间片到点 ≠ 程序主动让出：抢占是内核借定时器**中断**强行夺权，被抢占的进程对此毫无知觉——逻辑流连续的假象就是这么维持的。

## 工程关联

- **查看进程上下文的真实数据**：`cat /proc/<pid>/maps` 直接看到上图那套地址空间布局（栈、堆、各段、libc 映射、`[vdso]`、`[vvar]`）；`/proc/<pid>/status` 看进程状态（R/S/D/Z/T）、`VmRSS` 等。
- **测量上下文切换开销**：`perf stat -e context-switches,cpu-migrations ./a.out` 看一次运行触发了多少次上下文切换；`vmstat 1` 的 `cs` 列看全系统每秒切换次数。频繁切换（如锁竞争激烈、线程过多）会显著拖慢程序。
- **用户态/内核态时间分布**：`time ./a.out` 输出的 `real/user/sys`，其中 `user` 是用户模式 CPU 时间，`sys` 是内核模式（系统调用、缺页处理）时间。`sys` 偏高通常意味着系统调用过于频繁。
- **抢占式调度的可见性**：`top`/`htop` 里的 `%CPU` 和进程状态，本质是内核靠定时器中断周期性记账、按调度策略（CFS）分配时间片的结果；`chrt`/`nice` 可调整调度优先级。
- **并发的三种实现路线**（第 12 章预告）：进程（`fork`，地址空间隔离，靠 IPC 通信）、I/O 多路复用（`select`/`epoll`，单进程内手动切换逻辑流）、线程（共享地址空间，上下文切换最轻）。三者都是「让多个逻辑流并发」的不同工程权衡。
- **mode bit 的硬件落地**：x86-64 用 CPL（Current Privilege Level，存于 `CS` 段寄存器低 2 位）实现，Linux 只用 Ring 0（内核）和 Ring 3（用户）。`syscall`/`sysret`、`iret` 等指令负责在两个环之间切换。

## 实验题

**🧪 题 1：观察进程的私有地址空间布局**

```c
#include <stdio.h>
#include <stdlib.h>
int global = 42;             // .data
int bss_arr[1024];           // .bss
int main(void) {
    int local = 1;           // 栈
    int *heap = malloc(64);  // 堆
    printf("代码 main : %p\n", (void *)main);
    printf("全局 global: %p\n", (void *)&global);
    printf("栈   local : %p\n", (void *)&local);
    printf("堆   heap  : %p\n", (void *)heap);
    getchar();               // 暂停，方便看 /proc/<pid>/maps
    return 0;
}
```

要求：
- `gcc -O0 -no-pie -o addr addr.c`（`-no-pie` 让地址更接近书上经典布局）。运行后另开终端 `cat /proc/$(pgrep addr)/maps`。
- 把打印出的四个地址和 `maps` 里的段一一对应（代码段 `r-xp`、数据段 `rw-p`、堆 `[heap]`、栈 `[stack]`），验证「自底向上」的布局。
- 去掉 `-no-pie` 重新编译运行两次，对比地址是否变化——观察 ASLR（地址空间布局随机化）。
- 结论：每个进程看到结构一致但具体映射各异的私有地址空间。

**🧪 题 2：用 strace 区分用户态与内核态的边界**

```c
#include <unistd.h>
#include <stdio.h>
int main(void) {
    long sum = 0;
    for (long i = 0; i < 100000000L; i++) sum += i;  // 纯用户态计算
    printf("%ld\n", sum);                            // printf 内部触发 write 陷阱
    return 0;
}
```

要求：
- `gcc -O0 -o ub ub.c`，先 `time ./ub` 观察 `user` 远大于 `sys`（计算密集，几乎不进内核）。
- `strace -c ./ub` 统计系统调用次数与耗时，确认循环本身不产生任何系统调用，只有 I/O 和启动/退出阶段有。
- 把循环体改成每次都 `write(1,".",1)`，再跑 `strace -c` 和 `time`，观察 `sys` 时间和系统调用次数暴涨。
- 结论：用户态计算不进内核；每次系统调用都是一次「陷阱 → 内核模式 → 返回」的模式切换，频繁切换代价高昂。

**🧪 题 3：测量上下文切换的存在与开销**

要求：
- 写一个 `while(1);` 死循环程序，后台运行多个实例（数量 > CPU 核数），用 `perf stat -e context-switches,cpu-migrations -a sleep 5` 观察全系统每秒上下文切换数。
- 对比只运行 1 个实例 vs 运行 `2 × 核数` 个实例时 `context-switches` 的差异，理解「进程多于核数时内核必须靠时间片轮转」。
- 用 `taskset -c 0 ./loop` 把多个实例绑到同一个核，再看切换数变化。
- 结论：当可运行进程数超过核数，内核靠定时器中断驱动的上下文切换在多个逻辑流间轮转，这正是单核也能「并发」的物理实现。
