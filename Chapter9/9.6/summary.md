# §9.6 地址翻译

这一节把前面所有抽象（VP/PP、页表、PTE）落到**MMU 每次访存到底走了哪几步、查了哪几块内存**。主线是一条不断被加速的链路：先给出地址翻译的形式化定义（§9.6 引子）→ 把 SRAM cache 接进来，让 PTE 也享受缓存（§9.6.1）→ 用 TLB 专门缓存翻译结果，省掉查页表的内存访问（§9.6.2）→ 用多级页表把页表本身压缩到可承受的大小（§9.6.3）→ 用一个小系统把 TLB、多级页表、cache 三者串成一次完整翻译（§9.6.4）。四小节解决的是同一个问题的四个递进侧面：**翻译要不要碰内存、碰几次、查的表本身有多大、合起来怎么跑。**

- §9.6 引子：地址翻译的形式化定义，VPN/VPO 拆分，页命中与缺页的完整步骤
- §9.6.1：cache 摆在 MMU 后面、用物理地址寻址，PTE 也被缓存
- §9.6.2：TLB——专门缓存 PTE 的小 cache，命中即可零内存访问完成翻译
- §9.6.3：多级页表——用基数树压掉未映射区域的页表空间
- §9.6.4：端到端——TLB + 两级页表 + 物理寻址 cache 跑一次完整翻译

---

## 地址翻译的形式化定义

**🎯 一次翻译就是一个映射函数**

地址翻译是 MMU 把虚拟地址空间的元素映射到物理地址空间：

```
MAP: VAS → PAS ∪ {∅}
  MAP(A) = A'   若虚拟地址 A 处的数据在物理地址 A'
  MAP(A) = ∅    若 A 处的数据不在物理内存（缺页）
```

**🎯 虚拟地址的拆分：VPN + VPO**

页大小 P = 2ᵖ（x86-64 下 p = 12，P = 4 KB）。虚拟地址低 p 位是**页内偏移 VPO**，其余高位是**虚拟页号 VPN**：

```
虚拟地址 VA:  [ VPN（虚拟页号） | VPO（p 位页内偏移） ]
物理地址 PA:  [ PPN（物理页号） | PPO（p 位页内偏移） ]
```

**🎯 翻译只换页号，偏移原样照抄**

关键直觉：VPO 和 PPO **完全相同**，翻译只做一件事——把 VPN 换成 PPN。因为页内偏移描述的是"在这一页里的第几个字节"，同一份数据搬到哪个物理页，页内位置不变。所以 MMU 真正要查的只有 VPN → PPN 这张表，这正是页表干的事。

**🎯 页表基址寄存器 PTBR**

CPU 里有个专用寄存器 **PTBR**（x86-64 上就是 **CR3**），指向当前进程页表的起始（物理）地址。MMU 用它定位页表：`PTE 地址 = PTBR + VPN × 条目大小`。上下文切换换地址空间，本质就是改写 CR3 这一个寄存器。

**🎯 页命中的完整步骤（纯硬件，无 OS）**

```
1. CPU 把 VA 送给 MMU
2. MMU 用 VPN 算出 PTE 地址（PTBR + VPN×8），向 cache/主存请求 PTE
3. cache/主存返回 PTE
4. MMU 用 PTE 里的 PPN 拼出 PA（PPN ∥ VPO），向 cache/主存请求数据
5. cache/主存返回数据给 CPU
```

**🎯 缺页的完整步骤（陷入内核）**

```
1~3 同上，但第 3 步发现 PTE 的有效位 = 0
4. MMU 触发缺页异常，控制权交给内核缺页处理程序
5. 处理程序选牺牲页，脏则写回
6. 换入新页，更新 PTE
7. 返回，重新执行触发缺页的那条指令 → 这次走页命中
```

呼应 §9.3：缺页是**故障**，处理后**重执行**当前指令，而不是跳到下一条。

## cache 与虚拟内存的结合（§9.6.1）

系统里同时跑着两套机制：MMU 把 VA 翻译成 PA（虚拟内存），SRAM cache 缓存内存内容（加速访问）。把它们拼起来只有一个设计决策：**cache 用虚拟地址还是物理地址寻址？** 等价于问 cache 摆在 MMU 前面还是后面。

**🎯 结论：物理寻址，cache 摆在 MMU 后面**

绝大多数系统选物理寻址——**先翻译，后查 cache**：

```
CPU ──VA──▶ MMU ──PA──▶ L1 cache ──▶ 主存(DRAM)
                          ▲
                     cache 看到的是物理地址 PA
```

**🎯 结合的实质：PTE 也是普通内存数据，照样被缓存**

MMU 翻译一次地址，自己要先从内存**取 PTE**（PTE 有物理地址 PTEA），再用翻译结果**取数据**。cache 摆在 MMU 后面后，这**两次访存都先穿过 cache**：

```
② MMU 算出 PTEA（物理地址）──▶ 送进 L1 cache 找 PTE
③ 命中直接给 PTE；miss 才去 DRAM
④ MMU 拼出数据物理地址 PA ──▶ 再送进 L1 cache 找数据
⑤ 命中给数据；miss 才去 DRAM
```

不是给 cache 加特殊机制，而是**让 PTE 享受和普通数据一模一样的缓存待遇**。结果：一次页命中理论上要两次内存访问（取 PTE + 取数据），但两者都可能在 L1 命中，实际很少真捅两次 DRAM。

**🎯 物理寻址的三个好处（书里明说的）**

- **多进程的块能同时在 cache 里**：cache 用物理地址做标签，物理地址全局唯一，进程 A/B 的数据互不冲突，切进程不用清 cache
- **共享页天然共享 cache 行**：两进程经不同 VA 映射到同一物理页（libc、COW），物理地址只有一个，在 cache 里**只占一行**，自动共享；若用虚拟寻址，同份数据会按不同 VA 存成多份（别名问题），既浪费又难维护一致
- **cache 完全不用管保护**（最易漏、最体现设计思想）：权限检查（§9.5 的 PTE 许可位）是 **MMU 在翻译阶段就做完**的；轮到 cache 出场时合法性早已验证，cache 只管"这个物理地址的数据在不在我这"。**保护和缓存职责彻底分离**

## 用 TLB 加速地址翻译（§9.6.2）

**🎯 问题：每次翻译都要查页表，等于每次访存多一次内存访问**

§9.6.1 把 PTE 放进了 L1 cache，已经省了不少；但即便 L1 命中也要花几个周期，而且 PTE 可能被普通数据挤出 L1。能不能有个**更靠近 MMU、专门只装 PTE** 的超小 cache？这就是 TLB。

**🎯 TLB：翻译后备缓冲器，缓存的是 PTE 本身**

TLB（Translation Lookaside Buffer）是 MMU 里的一块小 SRAM cache，每行存一条 **PTE**。它和 §9.6.1 的 SRAM cache 是**两种不同的 cache**：

- SRAM cache（L1/L2/L3）缓存**内存内容**，用物理地址寻址
- TLB 缓存**翻译结果（PTE）**，用**虚拟页号 VPN** 寻址

**🎯 VPN 的再拆分：TLBT + TLBI**

TLB 自身也是组相联结构，于是 VPN 被进一步切成组索引和标记：

```
VPN:  [ TLBT（标记） | TLBI（组索引，t 组就 t 位） ]
```

T 组 TLB 用 TLBI 选组、TLBT 比标记，和普通 cache 的寻址逻辑一模一样，只是输入是 VPN 而非物理地址。

**🎯 TLB 命中：翻译全程不碰内存**

```
1. CPU 产生 VA，MMU 从中抽出 VPN
2. VPN → (TLBT, TLBI)，查 TLB
3. 命中！直接拿到 PPN，拼出 PA
4. 拿 PA 去 cache/主存取数据
```

全部在芯片内完成，**一次内存访问都不需要**——这是 TLB 的全部价值。

**🎯 TLB 不命中：回退到查页表，再把 PTE 装进 TLB**

```
3'. TLB miss → MMU 退而求其次，去 cache/主存查页表取 PTE
4'. 取回 PTE，顺手存进 TLB（可能驱逐一条旧 PTE）
5'. 用新 PTE 拼出 PA 继续
```

miss 多花的就是 §9.6.1 那次"查页表"的开销。由于程序的局部性，TLB 命中率通常极高（>99%），所以平均翻译开销趋近于零。

## 多级页表（§9.6.3）

**🎯 问题：单级页表太大，且大部分是空的**

x86-64 下若用单级页表，每进程要 2⁴⁸/2¹² × 8 B = **512 GB** 的 PTE 数组。而且进程地址空间绝大部分**未映射**（堆栈之间的巨大空洞），为这些根本不存在的页保留 PTE 是纯浪费。

**🎯 解法：把页表组织成层级（基数树）**

用多级页表，**未映射的整片区域，对应的下级页表根本不必存在**：

- **一级页表**：每个 PTE 负责虚拟地址空间的一大片（chunk）。若这片区域完全未分配，该 PTE 直接置空，**不需要二级页表**
- **二级页表**：只有被一级 PTE 指向的、确实有映射的片，才分配出来，进一步细分到具体物理页

CSAPP 的例子：一级表 1024 个条目各管 4 MB，二级表 1024 个条目各管 4 KB。一个只用了开头一点和栈顶一点的进程，绝大多数一级 PTE 为空，省掉的二级页表就是省下的内存。

**🎯 k 级页表的查找：逐级下钻**

```
虚拟地址 VPN 被切成 k 段，每段索引一级:
VA:  [ VPN1 | VPN2 | ... | VPNk | VPO ]
       │      │            │
       ▼      ▼            ▼
   一级表 → 二级表 → ... → k 级表 → PPN → 拼 PPO 得 PA
```

x86-64 实际是 4 级（PGD→PUD→PMD→PT）或 5 级，每级 9 位索引、512 条目一页，详见 §9.7 Intel 案例和 §9.1-9.5 summary 的内核数据结构部分。

**🎯 多级看似更慢，但 TLB 把代价抹平了**

k 级页表意味着一次翻译要 k 次内存访问（逐级取目录项）——看着比单级慢 k 倍。但**这些目录项同样被 TLB/cache 缓存**，TLB 命中时一次都不用查；只有 TLB miss 才真的走 k 级下钻。局部性保证了 miss 极少，所以多级页表用"偶尔的 k 次访问"换来了"省下的海量页表内存"，是稳赚的。

## 端到端地址翻译（§9.6.4）

**🎯 把 TLB + 多级页表 + 物理寻址 cache 串成一次完整访存**

CSAPP 用一个玩具系统（14 位虚拟地址、12 位物理地址、64 字节页、四路 TLB、两级页表、物理寻址的直接映射 cache）演示三套机制如何咬合。地址位的全局拆分是理解的钥匙：

```
虚拟地址 14 位:  VPN(8) ∥ VPO(6)
                 VPN 再拆:  TLBT(6) ∥ TLBI(2)        ← 喂给 TLB

物理地址 12 位:  PPN(6) ∥ PPO(6)        （PPO = VPO，照抄）
                 PA 再拆:   CT(6) ∥ CI(4) ∥ CO(2)    ← 喂给 cache
```

**🎯 一次访存的完整流水**

```
1. CPU 给出 VA
2. MMU 抽 VPN，拆成 TLBT/TLBI，查 TLB
   ├─ TLB 命中 → 直接得 PPN，跳到第 4 步
   └─ TLB miss → 走多级页表（VPN1 索一级、VPN2 索二级）取 PTE，得 PPN，回填 TLB
3. 拼出物理地址 PA = PPN ∥ VPO
4. 把 PA 拆成 CT/CI/CO，查物理寻址的 L1 cache
   ├─ cache 命中 → 返回数据，结束
   └─ cache miss → 去主存取，回填 cache
```

**🎯 三组拆分别搞混：VPN 拆给 TLB，PA 拆给 cache，VPO=PPO 是桥**

- VPN → (TLBT, TLBI)：**TLB 的寻址**
- VPN → (VPN1, VPN2, …)：**多级页表的逐级索引**（与 TLB 拆法独立，是 VPN 的另一种切法）
- PA → (CT, CI, CO)：**cache 的寻址**
- VPO 原样变成 PPO：翻译前后唯一不变的部分，是连接虚拟侧与物理侧的桥

把这三组拆分认清，§9.6.4 的例题（给个 VA，问 TLB 是否命中、PPN 多少、cache 是否命中、取出什么字节）就是纯机械的查表练习。

## 易错点

- VPO 和 PPO 完全相同，翻译只换页号不动偏移——别把页内偏移也当成要"翻译"的东西
- §9.6.1 的 SRAM cache 和 §9.6.2 的 TLB 是两种不同的 cache：前者缓存**内存内容**用物理地址寻址，后者缓存**PTE（翻译结果）**用 VPN 寻址，别混为一谈
- cache 摆在 MMU 后面、用物理地址寻址，所以 cache 不需要做权限检查——保护在翻译阶段由 MMU 查 PTE 许可位完成，cache 这层是干净的
- PTE 不是什么特殊存储，它就是主存里的普通数据，有自己的物理地址，照样进 L1 cache 和 TLB——"PTE 也被缓存"是 §9.6.1 的核心
- TLB 命中时翻译**零内存访问**（全在芯片内）；TLB miss 才退回去查页表，多的开销正是 §9.6.1 那次查表
- 多级页表省的是"未映射区域的下级页表"，不是把所有 PTE 都压缩了；已映射区域该有的 PTE 一条不少
- 多级页表看似把翻译变慢 k 倍，但目录项也被 TLB/cache 缓存，TLB 命中时一次内存都不查，平均开销没增加
- §9.6.4 里 VPN 有两种切法：拆成 (TLBT,TLBI) 是给 TLB 用的，拆成 (VPN1,VPN2) 是给多级页表用的，两者互相独立，做题别套错
- 单级页表 512 GB 的算法是 2⁴⁸/2¹²×8B，关键是地址空间稀疏，多级才有意义；别以为"多级是为了查得快"——它是为了省空间，查得快靠的是 TLB

## 工程关联

- PTBR 就是 x86-64 的 **CR3 寄存器**，存当前进程页表根的物理地址；上下文切换 `switch_mm` 时写 CR3，同时（视情况）刷 TLB——这是"私有地址空间"假象的硬件落点
- 切换进程要不要刷 TLB：早期全刷代价高，现代 x86 用 **PCID（进程上下文标识）** 给 TLB 条目打进程标签，切换免刷，避免 TLB 抖动——直接对应 §9.6.1"多进程块共存"的思想搬到了 TLB 上
- `cpuid` / `lscpu` 能看到 TLB 规格（如 L1 dTLB 64 项、L2 TLB 1536 项）；TLB 是稀缺资源，大数组随机访问会**TLB thrash**，用 2 MB/1 GB **大页（HugePage）** 减少页数、降低 TLB miss，是数据库/JVM 常见调优手段
- `perf stat -e dTLB-load-misses,dTLB-loads,iTLB-load-misses` 量化 TLB 命中率；TLB miss 高而 cache miss 不高，是"地址翻译瓶颈"的典型信号，换大页通常立竿见影
- 多级页表的逐级下钻在内核里就是 `pgd_offset→p4d_offset→pud_offset→pmd_offset→pte_offset_map`（见 §9.1-9.5 summary），MMU 硬件 walk 和这段软件 walk 逻辑完全一致，只是硬件每次访存都走、还有 TLB 兜着
- 物理寻址 cache 让 `fork` 后父子共享的物理页在 L1 里只占一行，COW 复制前两进程读同一份缓存——§9.6.1"共享页共享 cache 行"的直接收益
- VIPT（虚拟索引物理标记）是现实 L1 的折中：用 VPO（翻译前后不变的低位）并行索引 cache，同时等 MMU 出 PPN 做标记比对，把翻译和查 cache 重叠起来——这是 §9.6.1 物理寻址在工业实现上的提速版（书正文未展开，知道有这回事即可）

## 实验题

**🧪 题 1：测 TLB miss 对随机访问的惩罚**

```c
/* 在一大块内存上按页步长随机跳访问，制造 TLB miss */
#define NPAGES (1 << 20)        /* 2^20 页 = 4 GB 虚拟跨度，远超 TLB 覆盖范围 */
char *buf = mmap(NULL, (size_t)NPAGES * 4096, PROT_READ|PROT_WRITE,
                 MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
/* 先写入初始化（否则全映射到零页，测不到真实 TLB 行为） */
for (long i = 0; i < NPAGES; i++) buf[(size_t)i*4096] = 1;
/* 随机跳页累加，每次落在不同页 → 高概率 TLB miss */
long sum = 0;
for (long k = 0; k < 50000000; k++) sum += buf[(size_t)idx[k % NPAGES]*4096];
```

要求：
- `perf stat -e dTLB-load-misses,dTLB-loads,cycles,instructions ./a.out`，记录 dTLB miss rate
- 用 `mmap` 加 `MAP_HUGETLB`（或 `madvise(MADV_HUGEPAGE)`）改用 2 MB 大页重跑，对比 dTLB-load-misses 的下降幅度
- 解释：页数从 N 降到 N/512，TLB 每条覆盖 512 倍地址范围，miss 自然暴跌

**🧪 题 2：观察上下文切换是否刷 TLB**

要求：
