# §9.7.2-9.8 Linux 虚拟内存系统与内存映射

前面几节讲的是虚拟内存的「机制」——页表怎么翻译地址（§9.6）、PTE 权限位怎么做保护（§9.5）。这一节落到「Linux 具体怎么用这套机制」：内核用 `mm_struct` + `vm_area_struct` 把一个进程的地址空间组织成一串「区域（area）」，缺页处理就是拿地址去这串区域里查、再查权限；而所有区域的本质都是「把一段虚拟地址映射到某个磁盘对象」——这就是内存映射（memory mapping），fork / execve / mmap 全是它的不同用法。主线一句话：**地址空间不是一整块，而是一串各自映射到某个对象的区域；缺页 = 查区域 + 查权限 + 换页。**

## Linux 进程虚拟内存的组织：mm_struct 与 vm_area_struct

🎯 **两层数据结构**
内核为每个进程维护一个 `task_struct`（进程描述符），其中 `mm` 字段指向一个 `mm_struct`，它是这个进程整个虚拟内存的「总账本」。关键两个字段：

- `pgd`：页全局目录（page global directory）的**物理基址**——也就是第一级页表的起点。进程被调度上 CPU 时，内核把 `pgd` 装进 `CR3`，地址翻译就以它为根（呼应 §9.6 多级页表）。
- `mmap`：指向一条 `vm_area_struct` 的**链表**，每个结点描述地址空间里的一个「区域（area）」。

🎯 **vm_area_struct 描述一个区域**
一个「区域」是地址空间里一段**连续**、且**权限/映射来源一致**的页的集合（代码段、数据段、堆、每个共享库、栈各是一个或多个区域）。核心字段：

```c
struct vm_area_struct {
    unsigned long vm_start;   // 区域起始虚拟地址
    unsigned long vm_end;     // 区域结束（vm_start ~ vm_end-1）
    unsigned long vm_prot;    // 本区域内页的读写执行权限
    unsigned long vm_flags;   // 关键：共享(shared) 还是私有(private)
    struct vm_area_struct *vm_next;  // 链表指向下一个区域
};
```

`vm_prot` 决定这段页是 r/w/x 哪些位（和 PTE 权限位一致）；`vm_flags` 里记的 shared/private 决定写了之后回不回写对象（见后面 §9.8.1）。**`/proc/<pid>/maps` 的每一行，就是一个 `vm_area_struct` 的可读打印**。

整张「总账本」长这样——`pgd` 管「地址怎么翻译」（指向页表），`mmap` 管「这段地址合不合法、映射的是谁」（指向区域链表），两条线并行：

```
task_struct
   │ mm
   ▼
 mm_struct
   ├── pgd ───────────────▶ 页全局目录（PGD，物理基址）──装入 CR3──▶ 多级页表
   │                                                        （§9.6 地址翻译）
   └── mmap ──▶ vm_area_struct ──▶ vm_area_struct ──▶ vm_area_struct ──▶ NULL
                  vm_start/end       vm_start/end       vm_start/end
                  vm_prot=r-x        vm_prot=rw-        vm_prot=rw-
                  flags=private      flags=private      flags=shared
                     │ .text            │ .data            │ libc.so
                     ▼                  ▼                  ▼
              ┌──────────────── 进程虚拟地址空间 ────────────────┐
              │ [.text] [.data/.bss] [heap] ... [libc] [stack] │
              └────────────────────────────────────────────────┘
                每个 vm_area_struct 圈定其中一段连续区域
```

⚠️ **链表只是教学模型**
真实内核为加速「给定地址，找它落在哪个区域」的查找，额外用**红黑树**（早期）／**maple tree**（新版）组织这些区域。一个进程动辄几百上千个区域（每个 `.so`、每次 `mmap` 都新增），线性扫链表太慢。但概念上你记「一串区域」就够了。

## 内核虚拟内存：每个进程页表顶部那一段都一样

🎯 **内核区域被映射进每个进程**
用户栈之上的高地址段是内核虚拟内存。每个进程的页表里，这部分**映射到完全相同的物理内核代码和数据**——这样无论哪个进程陷入内核（系统调用、缺页、中断），看到的内核地址都一致，不用切页表。

```
高地址 ┌─────────────────────────────┐ ┐
       │  进程相关内核数据            │ │  每进程一份
       │  （页表、内核栈、task_struct）│ │  （内容各不同）
       ├─────────────────────────────┤ │  内核
       │  物理内存的直接(identity)映射 │ │  虚拟内存
       │  内核代码、全局数据           │ │  全进程相同物理页
       ├═════════════════════════════┤ ┘  ← 用户/内核分界
       │  用户栈 [stack]  ↓           │ ┐
       │            ⋮                 │ │
       │  共享库 libc.so (r-xp 共享)  │ │  用户
       │            ⋮                 │ │  虚拟内存
       │  运行时堆 [heap]  ↑          │ │  （每进程独立）
       │  .data / .bss               │ │
低地址 │  .text (r-xp 私有 COW)       │ ┘
       └─────────────────────────────┘
```


🎯 **两类内核内存**
- **进程相关**：页表本身、内核栈、`task_struct`/`mm_struct` 等——每个进程各有一份。
- **全进程共享**：内核代码、全局数据，以及对**全部物理内存的直接映射（identity mapping）**——内核可以用一段固定虚拟地址直接寻址任意物理页，做物理内存管理时很方便。

## Linux 缺页处理：三道关卡

🔧 **MMU 触发缺页后，内核 handler 依次问三个问题**
承接 §9.5，缺页异常进内核，`do_page_fault` 大致这样判：

1. **地址合法吗？** 拿出错虚拟地址 A，去遍历该进程的区域（红黑树查找）。**A 不落在任何 `vm_area_struct` 的 `[vm_start, vm_end)` 里 → 非法地址 → 发 `SIGSEGV`（段错误）。** 这就是野指针解引用崩溃的判定点。
2. **访问合法吗？** A 落在某区域里，但**操作类型违反该区域 `vm_prot`**（如对只读代码段执行写、对不可执行区取指）→ 保护违例 → 同样 `SIGSEGV`。这就是写字符串字面量崩溃的判定点。
3. **都合法 → 正常缺页**：选一个牺牲页换出（若需要），把缺的页从对象换入物理内存，更新 PTE，返回**重新执行**触发缺页的那条指令（呼应 §8.1 故障「返回当前指令」）。

```
缺页地址 A 进入 do_page_fault
        │
        ▼
  ┌─────────────────────────┐   否（A 不在任何区域）
  │ 关卡①：A 落在某区域内?    │ ───────────────▶ SIGSEGV（野指针）
  └─────────────────────────┘
        │ 是
        ▼
  ┌─────────────────────────┐   否（违反 vm_prot）
  │ 关卡②：操作符合该区域权限?│ ───────────────▶ SIGSEGV（写只读/取指不可执行）
  └─────────────────────────┘
        │ 是
        ▼
  ┌─────────────────────────┐
  │ 关卡③：正常缺页           │
  │ 换出牺牲页→换入缺页→更新PTE│ ───────────────▶ 返回，重执行该指令
  └─────────────────────────┘
```

⚠️ 段错误和「正常缺页」走的是同一个异常入口，区别只在 handler 里前两关有没有挂掉。所以「程序段错误」和「程序正常运行时换页」在硬件层面是同一件事的两种结局。

## 共享对象 vs 私有对象：写了之后回不回写对象（§9.8.1）

🎯 **对象的两种映射策略**
一个区域要么映射**普通文件**，要么映射**匿名文件**（内容全 0，对应 `.bss`/堆/栈，缺页时给一个置零页，不读盘）。映射时选策略，体现在 `vm_flags`：

- **共享对象（MAP_SHARED）**：修改**回写**磁盘对象，且**所有映射同一对象的进程都看得见**——物理内存只有一份，多个进程的 PTE 指向同一批物理页。用于 IPC、`mmap` 写文件。
- **私有对象（MAP_PRIVATE）**：修改**只对自己可见**、不回写——靠写时复制（COW）实现。典型是可执行文件的 `.data`/`.text`。

🎯 **写时复制 COW**
私有对象初始也让所有进程**共享同一批只读物理页**（`vm_flags` 标 private、PTE 标只读）。只读时零复制；一旦某进程**写**某页 → 触发保护故障 → handler 发现是 COW 区域 → **只复制被写的那一页**给它、改成可写、更新它的 PTE → 重新执行写指令。**复制只在「第一次写」发生、且按页（4KB）粒度**，没动过的页继续共享。

```
① 映射后（未写）           ② 进程 2 写该页 → 保护故障    ③ handler 复制该页
 进程1 PTE ─┐                进程1 PTE ─┐                  进程1 PTE ──▶ 物理页 P
            ├─▶ 物理页 P                 ├─▶ 物理页 P(只读)
 进程2 PTE ─┘ (只读, private) 进程2 PTE ─┘  ✗写触发故障     进程2 PTE ──▶ 物理页 P'(P的副本,可写)
   零复制，共享一份                                          只复制被写的那一页
```

| 映射策略 \ 对象 | 文件对象 | 匿名对象 |
|---|---|---|
| **共享 SHARED** | mmap 文件 IPC，写入回盘 | 共享内存 IPC，跨进程共享但不回盘 |
| **私有 PRIVATE** | `.text`/`.data`（COW） | `.bss`/堆/栈（COW + 按需置零页） |

## fork 与 execve 的内存映射视角（§9.8.2-9.8.3）

承接第一节的数据结构（`task_struct → mm_struct → vm_area_struct 链表 + pgd`），fork 和 execve 操作的是同一套账本，但动作相反：**fork 整本克隆账本，execve 给同一个人换一本全新账本**。

🔧 **fork：复制账本，不复制数据**
`fork` 创建子进程时，内核：① 复制父进程的 `mm_struct`、区域链表、页表；② 把**双方所有私有页的 PTE 都标成只读**，并把区域标为 private COW。于是父子初始共享全部物理页，**任何一方写某页才复制那一页**。这就是 fork 快、且父子私有数据互不影响的根本原因——把复制全部推迟到真正写的时刻、且只复制被写的页。

```
        fork 前                          fork 后
  父 task_struct                  父 task_struct      子 task_struct（新建,新PID）
       │ mm                            │ mm                 │ mm
       ▼                               ▼                    ▼
   mm_struct                       mm_struct            mm_struct(副本)
   pgd, mmap                       pgd, mmap            pgd', mmap'      ← 两套独立账本
       │                               │                    │
       ▼                               ▼                    ▼
   vma链表 → 物理页              vma链表 ─┐          vma链表(逐项复制)
                                          ├──▶ 同一批物理页（PTE 全标只读, COW）
                                          ┘
```

🔧 **execve：换一套区域，靠 demand paging 填**
`execve("a.out", ...)` 加载新程序时**不读程序到内存**，而是：① 删除当前进程已有的用户区域；② 建私有 COW 区域映射新程序的 `.text`/`.data`（来自 a.out 文件）和 `.bss`（匿名、置零）；③ 建共享区域映射用到的共享库（如 `libc.so`）；④ 把 PC 指向 `.text` 入口。**真正的代码/数据是第一次执行/访问触发缺页时才从磁盘换入的**（呼应 §9.4：execve 只建映射不读盘）。

```
        execve 前                       execve 后
   当前 task_struct ───────────── 还是同一个 task_struct（PID 不变, fd 默认保留）
       │ mm                            │ mm
       ▼                               ▼
   旧 mm_struct                    新 mm_struct（全新空白，旧的引用计数减→释放）
       │ mmap                          │ mmap
       ▼                               ▼
   旧 vma链表（整条拆除）          新 vma链表（按 a.out 的 ELF 重建）：
   .text/.data/.bss/堆/栈/库         .text/.data → 私有 COW 映射新文件
                                     .bss/堆/栈   → 匿名置零
                                     libc.so      → 共享映射
                                     PC 指向新 .text 入口
```

⚠️ **fork 复制的账本，execve 上来就拆**：shell 的 `fork + execve` 模式里，fork 辛苦复制的 vma 链表和页表，execve 紧接着全部销毁。正因如此 Linux 提供 `vfork`/`posix_spawn`/`clone(CLONE_VM)` 优化「fork 完马上 exec」——账本马上要丢，就别白复制。

⚠️ 多个进程跑同一个程序，`.text` 是只读/COW 的共享页——内核磁盘缓存里 `libc` 代码全系统只存一份物理页，所以开 100 个进程内存不会成比例暴涨。

## 用户级内存映射：mmap / munmap（§9.8.4）

🎯 **mmap 让用户态自己建区域**
`mmap` 是上面所有机制暴露给程序员的系统调用——你可以亲手创建一个 `vm_area_struct`：

```c
void *mmap(void *start, size_t length, int prot,
           int flags, int fd, off_t offset);
//  prot:  PROT_READ | PROT_WRITE | PROT_EXEC
//  flags: MAP_SHARED / MAP_PRIVATE，MAP_ANONYMOUS（匿名，不关联 fd）
//  返回映射区起始地址，失败返回 MAP_FAILED((void*)-1)
int munmap(void *start, size_t length);  // 删除区域
```

把文件 `fd` 从 `offset` 起的 `length` 字节映射进地址空间，之后**像访问内存一样读写文件**，不用 `read`/`write`——内核靠缺页按需把文件页换入。`MAP_ANONYMOUS` 则映射一段匿名置零内存（`malloc` 申请大块时底层就是它）。

🔧 **为什么 mmap 读大文件可能比 read 快**
`read` 是「磁盘 → 内核页缓存 → 用户缓冲区」两次拷贝；`mmap` 直接把内核页缓存的物理页映射进用户地址空间，**少一次拷贝**，且多进程映射同一文件能共享这份页缓存。代价是随机的缺页开销和不适合小文件。

```
read():  磁盘 ──DMA──▶ 内核页缓存 ──CPU 拷贝──▶ 用户缓冲区     （2 次搬运）
mmap():  磁盘 ──DMA──▶ 内核页缓存 ◀──映射 PTE──  用户地址空间   （省掉 CPU 拷贝）
                          └─ 多进程映射同一文件即共享这份页缓存
```

## 易错点

- 「地址空间是一整块连续内存」是错的——它是**一串离散的区域（vm_area_struct）**，区域之间有大段未映射的空洞，访问空洞就是段错误第一关挂掉。
- `mm_struct->pgd` 是**页表的物理基址**、`mmap` 是**区域链表头**，两者别混：前者管「地址怎么翻译」，后者管「这段地址合不合法、映射的是谁」。
- 段错误不是「内存不够」，而是缺页 handler 前两关（地址不在任何区域 / 操作违反区域权限）没过；真正换页是第三关，和段错误同入口不同出口。
- fork **不复制内存**，只复制页表并把私有页标只读——「fork 很慢因为要拷贝整个地址空间」是错的，慢的只是写得多导致 COW 复制多。
- execve **不把程序读进内存**，只删旧区域、建新区域映射；程序内容是运行时缺页换入的——所以大程序「启动」很快，慢在后续首次触摸各页。
- 共享对象的「一份物理页」发生在**缺页填入之后**（映射时只是约定指向谁）；私有对象的「复制」发生在**第一次写、按页粒度**——别把映射时刻和物理页存在画等号。
- `mmap` 的 `MAP_PRIVATE` 写文件**不会改到磁盘文件**（COW 到私有页），想改文件得用 `MAP_SHARED`。

## 工程关联

- `cat /proc/self/maps`：逐行就是 `vm_area_struct`。看权限位末位 `p`=private(COW)、`s`=shared；带路径的是文件映射（`/usr/lib/libc.so.6`、可执行文件本身），`[heap]`/`[stack]`/无名是匿名映射。这是把这两节全部概念落地的第一工具。
- `/proc/<pid>/smaps`：在 maps 基础上给出每个区域的 RSS、PSS、Shared/Private、Swap——能直接看出哪些页是共享的、COW 后变私有了多少。
- `strace ./a.out` 启动时能看到 `execve` → 一串 `mmap`（映射 ld.so、libc、可执行文件本身）→ `mprotect`（GOT 重定位后改只读，呼应 §7 RELRO）的标准序列。
- `perf stat` 的 `minor-faults`（页在内存、只需建映射，COW 复制属此类）vs `major-faults`（需读磁盘）——能区分缺页是「换页表」还是「等磁盘」。
- 数据库/`mmap`-based 存储引擎（LMDB、部分 RocksDB 路径）用 `mmap` 把数据文件直接映射进地址空间，靠内核页缓存做缓冲，省一次拷贝；缺点是页缓存换出时机不可控。
- 共享库全系统只存一份物理代码页（`.text` 共享/COW），是动态链接省内存的根本（呼应 §7.10-7.12）。

## 实验题

**🧪 题 1：用 /proc/self/maps 给地址空间「拍 X 光」**
写一个程序：① 定义一个全局已初始化数组、一个全局未初始化大数组、`malloc` 一块 1MB、`mmap` 映射一个文件；② 在每步之后 `system("cat /proc/self/maps")` 或读 `/proc/self/maps` 打印。
- 要求：找出 `.text`/`.data`/`.bss`/`[heap]`/你的 mmap 区域/`libc.so`/`[stack]` 各对应哪一行。
- 验证：① 可执行文件代码段权限是 `r-xp`、数据段 `rw-p`、共享库代码 `r-xp`；② `malloc` 1MB 后 `[heap]` 是否变大 vs 是否新增匿名区域（大块 malloc 会走 mmap 而非堆）；③ `mmap` 文件那行末尾带文件路径，权限位末位是 `p` 还是 `s` 取决于你传的 flag。

**🧪 题 2：亲眼看 COW 触发（minor fault 计数）**
父进程 `malloc` 并写满一块 64MB 内存（确保物理页都已分配），然后 `fork`；子进程**只读**遍历这块内存，再把它**全部改写**一遍。用 `getrusage(RUSAGE_SELF, ...)` 在子进程读改前后取 `ru_minflt`。
- 要求：对比「只读阶段」和「改写阶段」子进程 minor fault 的增量。
- 预期：只读阶段几乎不增（共享父页）；改写阶段 minor fault ≈ 64MB/4KB ≈ 1.6 万次——每页第一次写各触发一次 COW 复制。这把「复制发生在第一次写、按页粒度」量化出来。

**🧪 题 3：mmap MAP_SHARED vs MAP_PRIVATE 写文件**
创建一个内容已知的文件，分别用 `MAP_SHARED` 和 `MAP_PRIVATE` 映射它，各自改写映射内存的前几个字节，`munmap` 后再 `cat` 文件。
- 要求：观察两种 flag 下磁盘文件内容是否改变。
