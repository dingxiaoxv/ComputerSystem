# §9.9-9.10 动态内存分配与垃圾收集

前面几节虚拟内存给的是「机制」——地址翻译、缺页、区域映射。但程序员真正天天打交道的不是 `mmap` 这种页粒度的原始接口，而是 `malloc`/`free` 这种**字节粒度、运行时才知道大小**的分配。这一节就是讲 `malloc` 到底在那块叫「堆（heap）」的匿名区域里干了什么：它把内核按页给的一大块虚拟内存，切成大小不一的小块发给你、回收时再尽量拼回去。主线一句话：**动态分配器是用户态里一个「在堆这块虚拟内存上做空间记账」的库——核心矛盾是在「快」（吞吐率）和「省」（内存利用率）之间权衡，而所有数据结构（空闲链表、边界标记、分离桶）都是为了在 free 时能快速找到并合并碎片。**

§9.10 接着问一个问题：既然忘记 `free` 会泄漏，能不能让系统**自动**找出「再也用不到的块」并回收？这就是垃圾收集（garbage collection, GC）。核心洞察是把内存看成一张**可达图**——从根（寄存器/栈/全局里的指针）出发能走到的块才「活着」，走不到的就是垃圾。§9.9 的手动 `malloc`/`free` 和 §9.10 的自动 GC，是内存管理的两条路线：前者快但易错，后者省心但有运行时代价；理解了 §9.9 的块结构，才懂 GC 是如何在 `malloc` 找不到空闲块时介入、扫描这些块并回收的。

## 堆与 malloc/free 接口：分配器在哪块地、用什么和内核交易

🎯 **堆是一块向上生长的匿名私有区域**
每个进程地址空间里，`.bss` 之上有一块叫「堆」的区域（呼应 §9.8 的 `vm_area_struct`，匿名、私有、可读写）。内核维护一个指针 `brk` 指向堆顶。分配器通过两个途径向内核要这块「原料地」：

- `sbrk(incr)`：把 `brk` 上移 `incr` 字节，返回**移动前**的旧 `brk`（即新拿到的那段起点）；`incr` 为负则收缩堆。`incr=0` 时只返回当前 `brk`，可用来探测堆顶。
- 大块直接走 `mmap` 单独建匿名区域（见工程关联里的阈值）。

⚠️ 注意层级：`sbrk`/`brk`/`mmap` 是**系统调用**，一次拿一大片（页对齐、几十 KB 起）；`malloc`/`free` 是**用户态库函数**，在分配器从内核要来的这片里做字节级切分。`malloc` 绝大多数调用根本不进内核——只有堆里没有合适空闲块、需要扩张时才 `sbrk`/`mmap`。

🎯 **malloc / free 的契约**
```c
void *malloc(size_t size);   // 返回一个对齐的、至少 size 字节的块；失败返回 NULL
void  free(void *ptr);       // ptr 必须是 malloc/calloc/realloc 返回的指针
```
- 返回的地址满足**对齐要求**（x86-64 Linux 下 16 字节对齐，保证能放下任意标量类型，含 SSE）。
- `free(ptr)` 的 `ptr` 必须**恰好**是之前分配返回的地址，不能是块中间；分配器靠这个地址反查它管理的块头。
- `calloc` = `malloc` + 清零（且内部做大小溢出检查，呼应 §2.3）；`realloc` 调整已有块大小，可能原地扩、也可能重新分配并拷贝。

## 为什么要动态分配：编译期不知道大小

🎯 **大小依赖运行时输入**
很多数据结构的尺寸在编译期是未知的——读一个文件有多少行、网络收到多大的包、用户输入多长的字符串。静态数组只能猜一个上界（浪费 + 仍可能溢出）。动态分配让程序**到运行时拿到真实大小再申请**。

```c
// 编译期不知道 n，只能动态分配
int *a = malloc(n * sizeof(int));   // n 来自 argv / 文件 / 网络
if (!a) { /* 处理失败 */ }
...
free(a);
```

⚠️ 这正是 §2.3 提到的坑：`n * sizeof(int)` 可能整数溢出，导致申请的字节数远小于预期、随后越界写。安全代码要么用 `calloc(n, sizeof(int))`（内部查溢出），要么自己先校验 `n`。

## 分配器的两个目标：吞吐率 vs 利用率（一对死敌）

🎯 **两个相互拉扯的指标**
- **吞吐率（throughput）**：单位时间能完成多少次 `malloc`/`free`。要快，就希望操作是 O(1) 或接近常数。
- **峰值利用率（peak memory utilization）**：你真正请求的字节数（aggregate payload）占分配器向内核要来的总堆大小的比例。要省，就希望不浪费、碎片少。

```
            P_k = 到第 k 次请求为止「活着的 payload 总和」的历史峰值
利用率 U_k = max(P_i, i≤k) / H_k          H_k = 当前堆总大小
```
两者天然冲突：追求吞吐就想少花时间整理 → 容易留碎片 → 利用率低；追求利用率就要花时间合并、精挑细选空闲块 → 慢。**好分配器是在两者间找平衡，不是单点最优。**

⚠️ 利用率分母是「堆总大小 H_k」，而 H_k 只增不易减——一旦因某次峰值把堆撑大，后面就算 free 了，堆通常**不还给内核**（避免反复 `sbrk` 的开销）。所以「我 free 了为什么 RSS 不降」往往不是 bug。

## 碎片：内部碎片 vs 外部碎片

🎯 **内部碎片（internal fragmentation）：块比 payload 大**
已分配块的大小 > 你请求的 payload，差额浪费在块内部。来源：① 对齐填充（请求 1 字节也要凑到 16 对齐）；② 块头/边界标记等元数据占用；③ 分配器为简化管理，按最小块或规整尺寸向上取整。**内部碎片只取决于「过去的请求模式」，容易度量。**

```
malloc(1)  实际给一个 32 字节的块：
┌──────┬──────────────┬──────────┐
│ 头部 │ payload(1B)  │ 对齐填充  │   内部碎片 = 32 - 1 = 31 字节
└──────┴──────────────┴──────────┘
```

🎯 **外部碎片（external fragmentation）：空闲总量够、但没有一块连续够大**
空闲内存的**总和**满足请求，但被切成许多不连续的小块，没有任何单块装得下。

```
堆： [已用][空16][已用][空16][已用][空16]   空闲总 48B
malloc(40) → 失败！没有连续 40B 的空闲块（尽管空闲共 48B）
```

⚠️ 外部碎片**取决于未来请求**，无法事先预测，比内部碎片难对付得多。对抗它的主要武器就是后面的「合并（coalescing）」和「分离链表」。

## 隐式空闲链表：用块头把整个堆串成一条链

🎯 **块的格式：头部 + payload + （可选）填充**
每个块（无论空闲还是已分配）前面有一个字（word）当**头部（header）**，记录「块大小 + 是否已分配」。因为块按 8/16 字节对齐，大小的低 3/4 位恒为 0，正好**借最低位存 alloc 标志**：

```
头部（1 字，32 位示意）：
 31                     3   2   1   0
┌────────────────────────┬───┬───┬───┐
│      块大小 size        │ 0 │ 0 │ a │   a=1 已分配 / a=0 空闲
└────────────────────────┴───┴───┴───┘
  size 低位天然为 0 → 复用来藏标志位
```

🎯 **「隐式」从何而来**
空闲块没有显式指针互相链接——靠每个头部里的 `size` 字段，从一个块的起点加上 `size` 就跳到下一个块，**整个堆从头到尾被「隐式」串成一条链**。遍历 = 从堆起点顺着 size 一路跳到结尾哨兵块。

```
堆起点
  ▼
┌────┬──────┬────┬────────┬────┬────┐      ┌────┐
│ h  │ 已用 │ h  │  空闲   │ h  │... │ ...  │结尾 │  结尾哨兵：size=0,a=1
└────┴──────┴────┴────────┴────┴────┘      └────┘
  └─ size ─┘ 加 size 跳到下一块（无指针，故「隐式」）
```

⚠️ **隐式链表的致命缺点**：分配一次要从头扫整条链找空闲块，开销与**堆里块总数**（含已分配块）成正比——堆一大就慢。所以隐式链表是教学模型，真实分配器用显式/分离链表。

## 放置策略：在空闲链表里挑哪一块（§9.9.7）

🎯 **三种经典策略**
- **首次适配（first fit）**：从头扫，遇到第一个够大的就用。链表前部容易积累小碎片，后续搜索变慢。
- **下次适配（next fit）**：从上次停下的地方继续扫。比首次适配快，但研究表明利用率更差。
- **最佳适配（best fit）**：扫完整条链，选**最小的够用块**。利用率最好，但每次都要扫全表，最慢；且会产生大量难以再利用的微小碎片。

```
空闲块尺寸:  [16] [64] [32] [128]      请求 malloc(20→需24)
first fit →   ✗    ✓(64,切剩40)         选第一个够的 64
best  fit →   ✗         ✓(32,切剩8)     选最小够的 32（碎片更小但更慢）
```

🔧 简单分离存储/分离适配（见下）能把「best fit 的利用率」和「接近 O(1) 的速度」同时拿到，所以实际分配器走分离链表路线，而不是在单条链表上纠结这三种策略。

## 分割与扩张：拿到块之后怎么处理（§9.9.8-9.9.9）

🎯 **分割（splitting）**
选中的空闲块往往比请求大。若剩余部分 ≥ 最小块大小，就**把它切成两块**：前半给请求者（标已分配），后半留作新的空闲块。否则（剩余太小放不下一个块头+最小 payload）就整块给出去，多出来的成为内部碎片。

🎯 **向内核要更多堆（§9.9.9）**
找不到合适空闲块时，分配器调 `sbrk` 把堆扩张一大片（通常远大于本次请求，摊薄系统调用开销），把新空间作为一个大空闲块（并与原堆顶空闲块合并），再从中分配。

```
找不到合适块 → sbrk(扩张, 通常按页/大块) → 新空闲块并入堆顶 → 分割后返回
```

## 合并：把相邻空闲块拼回大块，对抗外部碎片（§9.9.10-9.9.11）

🎯 **为什么必须合并**
若 `free` 只是把当前块标空闲，相邻的两个小空闲块永远各自为政——这就是「假碎片（false fragmentation）」：明明挨着、合起来够大，却谁也用不了。所以 free 时要把**前后相邻的空闲块合并**成一个大块。

🎯 **合并后继块很容易，合并前驱块很难**
当前块向后跳（加 size）就能看到后继块的头部，判断它空不空 → **后向合并 O(1)**。但向前——你手里只有当前块起点，无法知道**前一个块**多大、从哪开始，没法回头看它的头部。这就需要边界标记。

🎯 **边界标记（boundary tags，Knuth 的技巧）**
在每个块的**末尾**再放一个**脚部（footer）**，内容是头部的副本（size + alloc）。这样当前块向前退一个字就能读到**前驱块的脚部**，立刻知道前驱块的大小和分配状态 → **前向合并也变 O(1)**。

```
块结构（带边界标记）：
┌──────┬───────────────┬──────┐
│ 头部 │   payload     │ 脚部 │   头部、脚部都存 (size|alloc)
└──────┴───────────────┴──────┘
free(当前块) 时：
  看后继块头部 → 空? 合并              （加 size 跳到后继）
  看前驱块脚部 → 空? 合并              （退一个字读前驱 footer）
四种情形：前后都已用 / 仅后空 / 仅前空 / 前后都空
```

⚠️ **边界标记的代价**：每个块多一个字的脚部，对**大量小块**是显著的内部碎片开销。优化：**已分配块不需要脚部**（脚部只在 free 时被相邻块查询，而被查的是空闲块）——于是把「前驱块是否已分配」这一位也塞进**当前块头部**的某个空闲位，已分配块就能省掉脚部，只有空闲块保留脚部。

## 显式空闲链表：只把「空闲块」串起来（§9.9.13）

🎯 **空闲块里塞前后指针**
隐式链表慢在「分配要扫过所有块（含已用）」。改进：空闲块的 payload 区反正没用，就在里面放 `pred`/`succ` 两个指针，把**所有空闲块**单独串成一条双向链表。分配时只遍历空闲块，搜索时间从「与堆总块数成正比」降到「与**空闲块数**成正比」。

```
空闲块（payload 区复用为指针）：
┌────┬──────┬──────┬─────┬────┐
│ 头 │ pred │ succ │ ... │ 脚 │   只有空闲块进链，已分配块不在链上
└────┴──────┴──────┴─────┴────┘
```

🎯 **链表排序策略影响吞吐**
- **LIFO（后进先出）**：free 的块插到链表头，分配/释放都 O(1)，最快；但利用率一般。
- **地址顺序**：按地址排序维护，free 要先找插入位置（更慢），但利用率更好。

⚠️ 显式链表要求块有最小尺寸（至少装下两个指针），增大了最小块、抬高小分配的内部碎片。

## 分离空闲链表：按大小分桶，实际分配器的主路线（§9.9.14）

🎯 **按大小区间分多条空闲链表**
维护一个数组，每个槽（桶）管一个大小类（size class），比如 `{1}, {2}, {3,4}, {5~8}, {9~16}, ...`（常按 2 的幂分档）。分配 `size` 时直接定位到对应桶、在桶内找块——大大缩短搜索。

```
size class 桶数组：
[ {1} ]──▶ 空闲块──▶ 空闲块
[ {2} ]──▶ 空闲块
[{3-4}]──▶ ∅
[{5-8}]──▶ 空闲块──▶ 空闲块──▶ 空闲块
   ⋮      malloc(6) → 直奔 {5-8} 桶，桶内首次适配
```

🎯 **两种风格**
- **简单分离存储（simple segregated storage）**：每个桶里的块大小**全一样**（取该类上界），不分割也不合并——分配/释放纯粹是从桶链头摘/挂，**O(1) 极快**；代价是内部+外部碎片都偏高。
- **分离适配（segregated fit）**：桶内块大小可不同，分配时在桶内找、可分割，free 时合并后挂回对应桶。**这是 glibc、tcmalloc 等真实分配器的核心思想**——它在「桶内只扫同类块」上拿到接近 best-fit 的利用率，又有接近 O(1) 的速度，正好化解了前面放置策略那对矛盾。

⚠️ 「分离链表是 best fit 的近似」：在大小类内做首次适配，约等于在全局做最佳适配，但只扫一个桶——这就是它能同时兼顾吞吐和利用率的原因。

## 垃圾收集：把堆看成可达图，自动回收走不到的块（§9.10）

🎯 **GC 是什么、什么时候介入**
垃圾收集器是一个**自动回收程序不再使用的已分配块**的运行时组件。有了它，应用只管 `malloc`（或语言里的 `new`），永远不用显式 `free`——GC 负责找出垃圾并归还给分配器。它通常在 `malloc` 找不到合适空闲块时被触发，或作为后台线程周期性运行。Lisp（McCarthy, 1960）最早引入，今天 Java/Go/Python/JavaScript 等都内置 GC。

🎯 **核心模型：可达图（reachability graph）**
GC 把内存抽象成一张有向图：
- **节点**分两类——**根节点（root）**：不在堆里但含指向堆的指针的位置（寄存器、栈上的局部变量、全局变量）；**堆节点**：每个已分配块是一个节点。
- **边** `p → q`：块 `p` 里存着一个指向块 `q` 内部的指针。

一个堆节点是**可达（reachable）**的，当且仅当存在一条从**某个根**出发到达它的有向路径。**不可达的节点 = 垃圾**（程序再也无法通过任何指针链访问到它），GC 就回收它们。

```
根（寄存器/栈/全局）
   r1 ──▶ [块A] ──▶ [块B]
   r2 ──▶ [块C]
              [块D] ──▶ [块E]     ← D、E 无任何根能到达 = 垃圾，可回收
可达：A、B、C        不可达：D、E
```

🎯 **Mark & Sweep（标记-清除）：经典两阶段算法**
最基础的追踪式 GC，分两趟扫描：
- **标记（mark）**：从每个根出发深度遍历可达图，给沿途每个可达块在头部置一个 **mark 位**。
- **清除（sweep）**：线性扫过整个堆的每个块，**未被标记**的块即垃圾、释放掉；被标记的块清掉 mark 位、留到下一轮。

```
mark 阶段：从根 DFS，可达块打标记
   [A✓][B✓][C✓][D ][E ]
sweep 阶段：扫全堆，未标记的 D、E 释放，已标记的清标记
   [A][B][C][freed][freed]
```
关键辅助操作（书中伪码）：`isPtr(p)` 判断 p 是否指向某个已分配块、`blockMarked(b)`/`markBlock(b)` 读写标记位、`length(b)`/`nextBlock(b)` 遍历堆。

🔧 **C 程序的保守式 GC（conservative GC）**
Java 这类语言运行时**知道每个内存位置的类型**，能精确分辨「这个字是指针还是整数」、指针指向哪。但 C/C++ 没有这种类型信息，GC 面临两个难题：

- **分不清指针和整数**：内存里一个看起来像地址的字，可能只是个恰好等于某块地址的整数。
- **指针可能指向块中间**：C 允许 `p = &block[5]`，GC 不能假设指针都指向块起点。

于是 C 的 GC（如 **Boehm-Demers-Weiser collector**）只能**保守**：把任何「看起来像指向某已分配块内部的字」都**当成指针**对待。后果是**宁可漏回收、绝不错回收**——某些其实是整数的值会被误判为指针，让本该是垃圾的块被「保住」，造成少量内存回收不掉，但绝不会误删还在用的块。`isPtr` 因此要支持「指向块内部也算可达」（用平衡二叉树/区间查找定位块）。

⚠️ **引用计数是另一条路，但治不了循环引用**
除了追踪式（mark-sweep），还有**引用计数（reference counting）**：每个块记一个「被多少指针指着」的计数，归零就立即回收（Python、C++ `shared_ptr` 用它）。优点是回收及时、无停顿；致命缺点是**回收不了循环引用**——`A→B→A` 互指，计数都不为 0，但从根已不可达，成了泄漏。所以 Python 在引用计数之外还跑一个追踪式 GC 专门收环。

## 工程实战：如何降低内存占用

承接上面那条「free 了 RSS 也不降」的现象——真实工程里「内存涨了下不来 / 占用过高」是高频问题。这一节系统梳理降内存的手段，从「先量准」到「少分配 / 复用 / 调分配器 / 还给内核」，按**先做哪个最划算**排序。

🔧 **第 0 步：先量准，别凭感觉优化**
不知道内存花在哪就动手，多半白忙。常用度量：
- `/proc/<pid>/status` 的 `VmRSS`（实际占的物理页）vs `VmSize`（虚拟地址空间，含没触摸的，参考价值低）；`/proc/<pid>/smaps_rollup` 一行汇总 RSS/PSS/Private/Shared/Swap。
- **PSS（按比例的共享内存）** 才是多进程下「这个进程该摊多少」的公平口径，统计整机内存别用 RSS 重复计共享页。
- **堆 profiler 定位是谁分配的**：`valgrind --tool=massif`（带调用栈的堆快照）、jemalloc 的 `prof`、tcmalloc/gperftools 的 heap profiler、`bytehound`/`heaptrack`。
- 关键判断：RSS 高是**真的在用**（那就得从数据结构下手）还是**碎片 / 分配器不归还**（那就调分配器或主动 trim）——两条路完全不同。

🔧 **手段一：少分配——从数据结构和布局下手（收益最大）**
最有效的降内存往往不在分配器，而在「根本少要」：
- **减少指针**：64 位下每个指针 8 字节，指针密集的结构（链表、树、`map<K,V*>`）开销巨大。用**索引/偏移**（`uint32_t`）代替指针能省一半；用紧凑数组替代链表还顺带改善 cache（呼应第 6 章）。
- **字段重排消 padding**（呼应 §3.9 对齐）：把大字段排前、小字段聚拢，能显著缩小结构体。
```c
struct Bad  { char a; long b; char c; };  // sizeof=24（两处 padding）
struct Good { long b; char a; char c; };  // sizeof=16
```
- **小对象优化（SSO / small-buffer optimization）**：短字符串/小数组直接内联存在对象里，免去一次堆分配——`std::string`、`absl::InlinedVector`、`llvm::SmallVector` 都这么做。
- **位压缩**：布尔标志用位域 / `bitset`；枚举用小整型；冷数据用变长编码（varint）、字典编码、delta 编码。
- **SoA 替代 AoS**：结构体数组 → 数组的结构体，去掉每元素的 padding 并利于压缩。

🔧 **手段二：复用而非反复申请——对象池 / arena**
频繁 `malloc`/`free` 既慢又留碎片。让同生命周期的对象「一起生、一起死」：
- **对象池（object pool）**：预分配一批固定大小对象，用完归还池里复用，不还给分配器——避免反复进 malloc、几乎零碎片。
- **arena / region 分配**：一次申请一大块，在里面线性 bump 指针分配，**整批一次性释放**（不单独 free 每个对象）。适合「一个请求 / 一帧 / 一次解析」周期内大量临时小对象——请求结束整块丢弃。Nginx 的 `ngx_pool_t`、protobuf 的 Arena、Rust 的 `bumpalo` 都是这个模式。
```
arena: [████ obj1 | obj2 | obj3 | ...     ] ── 请求结束整块 reset，O(1) 释放全部
```
- 这一招直接消灭外部碎片：同周期对象连续摆放，释放是整块归还而非零散 free。

🔧 **手段三：换 / 调分配器**
不改业务代码，换分配器常有立竿见影的效果：
- **换 jemalloc / tcmalloc / mimalloc**：它们的分离桶 + 线程本地缓存比 glibc `ptmalloc2` 碎片更少、多线程扩展更好。`LD_PRELOAD=/usr/lib/libjemalloc.so ./app` 即可零改动试。
- **调 glibc 参数**：`MALLOC_ARENA_MAX=2` 限制 arena 数（默认随核数膨胀，多核服务虚拟内存常因此暴涨）；`M_MMAP_THRESHOLD` / `M_TRIM_THRESHOLD` 通过 `mallopt` 或环境变量调。
- **主动归还**：glibc 的 `malloc_trim(0)` 在空闲时把堆顶连续空闲页还给内核（注意：堆中间的空闲块还不掉，受 §9.9 「堆只能从顶部收缩」限制）。

🔧 **手段四：把内存真正还给内核**
让 RSS 下降，最终要靠归还物理页：
- **大块走 `mmap` + `munmap`**：超过 `M_MMAP_THRESHOLD`（默认 ~128KB）的分配单独 `mmap`，`free` 时直接 `munmap`，RSS 立刻降——这就是「大块 free 后内存真降、小块不降」的原因。
- **`madvise(MADV_DONTNEED)`**：告诉内核「这段页内容不要了」，立即回收物理页（再访问触发缺页给零页）；**`MADV_FREE`** 更惰性——标记可回收，内存紧张时才真收，没压力时还能复用，开销更低。
- 注意 **THP（透明大页）** 的取舍：能减少 TLB miss（呼应 §9.6），但会让小分配也占 2MB 整页，反而**放大 RSS**；内存敏感服务常关掉或设 `madvise` 模式。

⚠️ **优化次序与陷阱**
- 次序：先量准 → 改数据结构（收益最大、最持久）→ 对象池 / arena → 换 / 调分配器 → madvise 归还。先换分配器图省事，常只是把碎片问题挪了个位置。
- 「RSS 不降」不等于泄漏：分配器缓存 + 堆不收缩是设计使然；用 massif / heaptrack 确认「分配点的存活量」是否真在涨，再判断是泄漏还是缓存。
- 省内存常和省时间冲突：对象池/arena 拿空间换时间的反面是「池占着不放」；压缩编码省内存但增 CPU。按瓶颈取舍，别无脑压。

## 易错点

- `sbrk`/`mmap` 是系统调用、一次要一大片；`malloc`/`free` 是用户态库、在那片里切字节——别把「`malloc` 一次 = 进一次内核」当真，多数 `malloc` 根本不进内核。
- `free` 后 RSS / 堆大小通常**不降**——分配器把空闲块留着复用，不还给内核（避免反复 `sbrk`）；「free 了内存没还」往往是设计如此，不是泄漏。
- 内部碎片由**过去的请求**决定、可度量；外部碎片由**未来的请求**决定、不可预测——两者成因和对策完全不同，别混。
- 头部能藏 alloc 标志，是因为**块按 8/16 对齐 → size 低几位恒为 0**，复用这些零位；不是额外开了字段。
- 合并时「后向合并易、前向合并难」——前向合并难是因为手里没有前驱块的起点和大小，**边界标记（脚部）就是专门为前向合并 O(1) 而设**。
- `free(p)` 的 `p` 必须是 malloc 返回的**那个地址**，不能 +偏移、不能重复 free、不能 free 栈/全局地址——分配器靠 `p` 前一个字反查块头，传错直接破坏堆元数据（典型 heap corruption）。
- 隐式空闲链表分配是 O(堆内总块数)，不是 O(空闲块数)——慢就慢在每次都得跨过已分配块；显式/分离链表才只扫空闲块。
- 「最佳适配利用率一定最好」要打折：best fit 会切出大量极小、难再用的碎片；实际分离适配靠分桶规避了这个问题。
- 「垃圾 = 没用的数据」不准确——GC 的「垃圾」是**从根不可达的块**，哪怕里面数据有意义，只要程序再也走不到它就是垃圾；反过来，一个你逻辑上「不再需要」但仍被某指针指着的块，GC 认为它可达、不回收（这就是「逻辑泄漏」）。
- 引用计数 ≠ 能回收一切：循环引用计数永不归零，必须配追踪式 GC 才能收环；别以为 `shared_ptr`/Python 引用计数就万无一失，环要用 `weak_ptr`/弱引用打断。
- C 的保守式 GC 是「宁漏勿误」：它会把恰好像地址的整数误当指针而**少回收**一些块，但绝不会误删活块——所以保守 GC 偶有内存涨、但不会因 GC 而崩。
- GC ≠ 没有内存问题：仍可能因「持有不该持有的引用」（缓存/监听器/全局集合只增不删）造成泄漏，只是不会有 use-after-free/double-free。

## 工程关联

- **glibc 的 `ptmalloc2`**：本质是分离适配 + 多个 arena（减少多线程锁竞争）+ fastbin/tcache（小块缓存，类似简单分离存储做到 O(1)）。理解了 §9.9 的边界标记/分离桶，就能读懂 `malloc.c` 的 chunk 结构（`prev_size`/`size` 头部、低位的 `PREV_INUSE` 标志正是「前驱是否已分配」那一位）。
- **brk vs mmap 阈值**：glibc 默认 `M_MMAP_THRESHOLD ≈ 128KB`——小于它走堆（`brk` 扩张、可复用）；大于它单独 `mmap`（free 时直接 `munmap` 还给内核，所以大块 free 后 RSS 会真降）。可用 `mallopt(M_MMAP_THRESHOLD, ...)` 或环境变量 `MALLOC_MMAP_THRESHOLD_` 调。
- **`strace` 看分配器和内核的交易**：循环小 `malloc` 只在堆不够时偶尔出现 `brk`；一次大 `malloc` 立刻出现一行 `mmap(..., MAP_ANONYMOUS, ...)`。这把「字节级 malloc」和「页级系统调用」的分层直接看出来。
- **`/proc/<pid>/maps`（呼应 §9.8）**：小分配撑大 `[heap]` 那一行；大分配新增一条独立匿名映射区域。free 后再看，能验证「堆不收缩、mmap 区被 munmap」。
- **内存调试工具**：`valgrind --tool=memcheck` 检测越界/重复 free/泄漏，靠的就是替换分配器并在每块周围加红区（redzone）；ASan（`-fsanitize=address`）同理用 shadow memory + redzone。理解块头/边界标记才懂它们怎么发现「写越界踩到了相邻块的头部」。
- **各语言的 GC 路线**：Java HotSpot 用**分代** mark-sweep-compact（新生代复制、老年代标记整理），G1/ZGC 进一步做并发低停顿；Go 用并发三色标记-清除（写屏障保证并发正确）；Python 用**引用计数为主 + 追踪式 GC 收环**；JS V8 也是分代。全都是 §9.10 mark-sweep + 可达图思想的工程化扩展。
- **C/C++ 里用 GC**：链接 Boehm GC（`libgc`/`-lgc`），用 `GC_malloc` 替代 `malloc` 且不必 `free`，它就是教科书级的**保守式** mark-sweep；适合不想手动管理生命周期、又不能换语言的场景。
- **valgrind 的 leak 分类正是可达性分析**：`--leak-check=full` 把泄漏分成 `definitely lost`（无任何指针可达，真泄漏）/`still reachable`（退出时仍有指针指着，常是全局缓存）/`indirectly lost`——这套划分本质就是 GC 的「从根可达否」，把 §9.10 的图模型直接用在了诊断上。
- **stop-the-world 停顿**：追踪式 GC 标记时通常要暂停应用（保证可达图不被并发修改），停顿时间是延迟敏感服务（交易、游戏）的核心指标——这就是为什么 ZGC/Shenandoah/Go GC 拼命做「并发标记 + 写屏障」把停顿压到亚毫秒。

## 实验题

**🧪 题 1：用 strace 看清 malloc 的 brk/mmap 分界**
写程序：① 连续 `malloc(64)` 一千次（小块）；② 再 `malloc(1<<20)`（1MB，大块）一次；③ 分别 `free`。
```c
#include <stdlib.h>
int main(void){
    for(int i=0;i<1000;i++){ void*p=malloc(64); /* 留住不 free，逼堆增长 */ }
    void *big = malloc(1<<20);
    free(big);
    return 0;
}
```
- 要求：`strace -e trace=brk,mmap,munmap ./a.out`，统计出现了几次 `brk`、几次 `mmap`。
- 验证：① 1000 次小 `malloc` 只触发**少数几次** `brk`（每次扩一大片，多数 malloc 不进内核）；② 那次 1MB `malloc` 对应**一行 `mmap(..., MAP_ANONYMOUS|MAP_PRIVATE, -1, 0)`**，`free(big)` 对应一行 `munmap`——印证「大块走 mmap、free 时真还给内核」。
- 进阶：用 `mallopt(M_MMAP_THRESHOLD, 64)` 把阈值调到 64 字节，再跑，观察小 malloc 也开始走 mmap。

**🧪 题 2：亲手验证外部碎片**
申请大量小块，`free` 掉**偶数下标**那一半（制造空洞），再尝试一次大 `malloc`，对比「空闲总量」和「能否分配成功」。
```c
#define N 100000
void *p[N];
for(int i=0;i<N;i++) p[i]=malloc(64);     // 全占满
for(int i=0;i<N;i+=2) free(p[i]);          // 释放一半，留下交错空洞
// 此时空闲 ≈ N/2*64 ≈ 3MB，但都是 64B 的不连续空洞
void *big = malloc(1<<20);                 // 请求连续 1MB
printf("big=%p\n", big);
```
- 要求：观察 `big` 是否为 `NULL`（多数情况能成——因为大块走 mmap 绕开了碎片堆，这恰好说明分配器的设计），再把请求改成「在堆内、小于 mmap 阈值的中等块」对比。
- 目的：体会外部碎片是「空闲总量够、连续块不够」，以及真实分配器为何要把大块隔离到 mmap。

**🧪 题 3：可视化块头与对齐填充（内部碎片）**
连续 `malloc(1)`、`malloc(17)`、`malloc(32)`，打印返回指针，并读取指针**前一个字**（glibc chunk 的 size 字段）。
```c
size_t chunk_size(void*p){ return *((size_t*)p - 1) & ~0x7UL; } // 清掉低 3 标志位
void *a=malloc(1), *b=malloc(17), *c=malloc(32);
printf("malloc(1)  实际 chunk=%zu, payload 浪费=%zu\n", chunk_size(a), chunk_size(a)-1);
printf("相邻两次返回地址差=%ld\n", (char*)b-(char*)a);
```
- 要求：观察 `malloc(1)` 实际占用远大于 1（最小 chunk，通常 32 字节）、返回地址按 16 对齐、相邻分配地址差体现了「块大小 = 头部 + 对齐后的 payload」。
- 验证：把请求从 1 逐步加到 24、25，观察 chunk 大小**阶梯式跳变**（每跨一个对齐档跳一级），这正是内部碎片随对齐产生的直接证据。

**🧪 题 4：用 valgrind 区分「可达 vs 不可达」泄漏（GC 可达性的实证）**
写一个程序，制造两种「没 free」的块：① 一块只被局部指针指着、函数返回后指针丢失（不可达）；② 一块挂在一个**全局指针**上（退出时仍可达）。
```c
int *g;                                   // 全局根
void lose(void){ int *p = malloc(64); }   // ① p 出作用域即不可达 → definitely lost
int main(void){
    lose();
    g = malloc(64);                        // ② 始终被全局 g 指着 → still reachable
    return 0;                              // 两块都没 free
}
```
- 要求：`gcc -g a.c && valgrind --leak-check=full ./a.out`，看报告里 `definitely lost` 和 `still reachable` 各是哪一块。
- 验证：① 那块算 **definitely lost**（无根可达，等价于 GC 眼里的垃圾）；② 全局 `g` 指的那块算 **still reachable**（从根可达，GC 不会回收它）。这把 §9.10 的「可达图」直接对应到了实际诊断工具的分类。
- 进阶（可选）：装 `libgc-dev`，把 `malloc` 换成 `GC_malloc`、全部不 `free`、链接 `-lgc`，观察保守式 GC 自动回收不可达块，亲手验证「不用 free 也不泄漏」。
